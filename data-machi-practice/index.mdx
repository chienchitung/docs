前 30 天系列主要回答「企業 AI 工作流為什麼要這樣設計」；實作篇則回答「真正打開專案後，第一步要做什麼」。

這套文章參考 Data Machi 的開源專案架構，但不要求讀者一開始就理解所有程式碼，也不會使用真實企業名稱、內部文件、試算表 ID、帳號或業務資料。所有操作都應使用自己建立的匿名測試資料。

## 這不是程式碼說明書

對初學者而言，直接看到一段 Python 或 React 程式碼，通常無法判斷：

- 這段程式應該放在哪個檔案？
- 執行前要先準備什麼？
- 它解決的是哪個問題？
- 執行成功時應該看到什麼？
- 發生錯誤時要檢查哪一層？

因此每篇文章都會依照相同順序撰寫：

```text
真實問題與使用情境
   ↓
用白話比喻理解概念
   ↓
確認它在整體架構的位置
   ↓
準備環境與測試資料
   ↓
逐步實作
   ↓
觀察預期結果
   ↓
排除常見錯誤
   ↓
完成驗收清單
```

## 你需要具備什麼程度？

不需要是軟體工程師，但建議先具備：

- 能使用終端機切換資料夾與執行指令
- 看得懂基本 Python 變數、函式與 `if`
- 知道 JSON 是一種資料格式
- 願意從錯誤訊息中找關鍵字

<Note>
  遇到看不懂的程式碼，不需要立刻理解每一個符號。先回答三個問題：輸入是什麼、輸出是什麼、這段程式負責哪一層。通常就能掌握七成用途。
</Note>

## 建議學習方式

不要一次讀完十篇。每完成一篇，至少做一次自己的小改動，例如：

- 更換一個測試欄位
- 新增一個 Prompt 規則
- 刻意製造一次錯誤
- 多加一份匿名 PDF
- 修改一個進度提示

只有親自改動並觀察結果，才會從「看懂文章」走向「真的會實作」。

## 去識別化原則

實作過程請一律使用：

```text
Your Organization
Demo Project
Team Member A
Demo Requests Sheet
Demo Policy.pdf
```

不要在公開程式碼、文章、截圖或錄影中出現：

- 真實公司與部門名稱
- 員工姓名、Email 與帳號
- 真實營運數字或政策內容
- Sheet／Board／Space ID
- API Key、Token 與 Service Account
- 內部網址與未公開文件

</Info>
