前面的實作建立了聊天、資料工具、文件搜尋、記憶與可靠性。最後一篇要把系統從「會回答問題」推進到「能協助完成工作」：將會議錄音整理成記錄，再把行動項目轉成可追蹤任務，最後完成前後端部署。

## 先理解閉環工作流

很多 AI 工具只停在摘要，但真正的知識工作還包含後續追蹤：

```text
會議錄音
   ↓
語音轉文字
   ↓
整理摘要、決策與待辦
   ↓
建立 Action Items
   ↓
持續追蹤狀態
   ↓
未來對話可引用會議背景
```

這就是從「產生內容」走向「推動工作」。

## Step 1：處理音訊格式

瀏覽器錄音常見格式是 WebM／Opus，但語音服務不一定直接支援。後端通常先用 ffmpeg 轉成標準格式。

```bash
ffmpeg -i meeting.webm meeting.wav
```

這一步是媒體格式轉換，不是 AI。若轉檔失敗，後面的模型再強也無法處理。

## Step 2：語音轉錄

將音訊送到語音辨識服務，取得逐字稿。逐字稿應保留：

- 原始檔名
- 建立時間
- 語言
- 音訊長度
- 轉錄狀態

初學者可以先用一段 30–60 秒的匿名測試錄音，不要直接上傳真實公司會議。

## Step 3：產生結構化會議記錄

不要只要求模型「幫我摘要」，而是定義固定 Schema：

```json
{
  "title": "Demo Project Sync",
  "summary": "...",
  "decisions": ["..."],
  "action_items": [
    {
      "task": "Prepare demo dataset",
      "owner": "Team Member A",
      "due_date": "2026-08-05"
    }
  ]
}
```

結構化輸出才能被前端轉成看板卡片，也方便後續匯出與搜尋。

## Step 4：建立 Action Items 看板

最小版本可以有三個狀態：

```text
To Do → Doing → Done
```

每張卡片至少包含：

- 任務名稱
- 負責角色
- 截止日期
- 來源會議
- 目前狀態

若資料只存在個人瀏覽器，可使用 IndexedDB。它比 localStorage 更適合儲存結構化記錄與較大內容。

## Step 5：把會議記錄加入對話上下文

使用者勾選某幾筆會議後，前端可以把整理後的摘要傳給後端：

```json
{
  "active_meetings": [
    {
      "title": "Demo Project Sync",
      "content": "Summary... Decisions... Action Items..."
    }
  ]
}
```

不要把整份逐字稿無限制塞進 Prompt。應限制單筆與總字數，避免上下文爆量。

## Step 6：部署前端與後端

常見部署方式：

```text
Frontend：Vercel
Backend：Render 或其他 Python 服務
```

正式環境需要設定：

- 前端的後端 API URL
- 後端 `ALLOWED_ORIGINS`
- 模型與外部服務 Secret
- Python 與 Node 版本
- 健康檢查路徑

Secret 應放在部署平台的環境變數，不要寫入 Repository。

## 不要直接複製原專案的企業設定

這套實作篇參考開源架構，但讀者應自行替換為：

- 自己建立的測試試算表
- 匿名 PDF
- 測試專案看板
- 通用角色名稱
- 自己的部署網域

<Warning>
  公開 Repository 不等於其中所有設定都適合原樣複製。實作時仍要檢查是否有預設 Sheet ID、網域、角色名稱或資料 Schema，並改成自己的匿名測試環境。
</Warning>

## 完成後你真正學會了什麼？

你不只是做出一個聊天介面，而是完成了：

```text
API 契約
+ 模組化 Prompt
+ 結構化資料工具
+ 文件 RAG
+ LangGraph 工作流
+ 多輪記憶與釐清
+ Timeout／Fallback／Verification
+ Agent UX
+ 會議到行動項目的閉環流程
+ 前後端部署
```

<Info>
  實作篇的目的不是讓你複製一個現成 Agent，而是讓你看懂每一層為什麼存在，並能替換成自己的資料、規則與工作流程。
</Info>
