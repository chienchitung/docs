Demo 只要成功一次就很吸引人；產品則必須在 API 逾時、模型過載、工具查無資料與憑證失效時，仍然讓使用者知道發生什麼事。

## 四個不同機制

| 機制 | 解決問題 |
| --- | --- |
| Timeout | 避免請求無限等待 |
| Retry | 處理短暫性錯誤 |
| Fallback | 主模型失敗時切換其他模型 |
| Verification | 對照工具結果，檢查回答是否有依據 |

## 不要讓所有步驟使用同一個時間上限

分類與路由通常應快速完成，長篇報告則需要更長時間。查核也應有總預算，避免使用者一直停在「驗證中」。

## 錯誤訊息要能引導下一步

例如「模型服務暫時過載，請稍後重試」和「Google Sheet 尚未分享給 Service Account」是完全不同的問題，不應都顯示成「請檢查 API Key」。

## 驗收方式

刻意製造錯誤：移除金鑰、使用不存在的 Sheet、讓模型名稱無效、查詢不存在的 PDF。確認前端顯示的訊息能幫助使用者採取正確行動。
