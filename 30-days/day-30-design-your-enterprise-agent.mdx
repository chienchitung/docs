走到第 30 天，我們從一個能回答問題的聊天模型，一路建構出具備 RAG、工具呼叫、Agent 路由、LangGraph 狀態機、會議工作流、可靠性設計與企業部署的完整知識工作系統。最後的問題不再是「還能加什麼新框架」，而是：**如何把這些能力，用在你自己真實的工作情境裡？**

## Agent 成熟度六階段

企業 AI 工作流的能力可以分成六個成熟階段，每一階段都有明確的核心問題需要回答。

| 階段 | 核心能力 | 關鍵問題 |
| --- | --- | --- |
| **Level 1：Chat** | 根據模型既有知識回答問題 | AI 能回答什麼？ |
| **Level 2：RAG** | 查詢企業內部文件與知識庫 | AI 能找到公司資料嗎？ |
| **Level 3：Tool Use** | 存取外部系統、資料庫、API | AI 能查表與看進度嗎？ |
| **Level 4：Agent** | 自行決策、選擇工具、多步推理 | AI 知道下一步要做什麼嗎？ |
| **Level 5：Workflow** | 狀態管理、路由邏輯、驗證機制 | AI 能穩定完成複雜流程嗎？ |
| **Level 6：Product** | 安全、可靠、可觀測、可維護 | 員工願意每天依賴這個系統嗎？ |

<Note>
  大多數 AI 應用的 Demo 停留在 Level 1–2，讓人以為「有了 LLM 就能解決一切」。真正讓企業願意投入使用的系統，需要從 Level 3 開始認真設計，並在 Level 6 的工程紀律中找到可信度。
</Note>

### Data Machi 的現況與路線圖

Data Machi 目前已進入 **Level 5**，核心功能涵蓋：

- ✅ RAG 知識庫查詢（Level 2）
- ✅ 試算表工具呼叫（Level 3）
- ✅ LangGraph 路由與狀態管理（Level 4–5）
- ✅ 會議轉錄與結構化輸出（Level 5）
- 🔄 逐步補齊 Level 6 的錯誤處理、測試、效能與 UX

## 企業 Agent 設計 Canvas

在動手開發之前，回答這七個問題，能幫你把模糊的「想做一個 AI 助理」具體化成可以執行的系統設計。

<Steps>
  <Step title="使用者真正要完成的工作是什麼？">
    不是「我想要一個 AI 聊天機器人」，而是「業務人員每週需要花 3 小時手動從 CRM 和郵件中整理客戶跟進清單，我想讓這件事自動化」。

    **思考方式：** 先找到一個具體的、重複發生的、目前靠人工完成的工作任務。AI 工作流最適合的目標，是那些「有明確輸入、有標準流程、有可驗證輸出」的任務。

    ```text
    ❌ 模糊目標：「幫助員工更有效率」
    ✅ 具體目標：「每次有新客戶詢問，自動從知識庫提取相關產品規格，
                  生成個人化的初步回覆草稿，供業務人員確認後發送」
    ```
  </Step>
  <Step title="工作目前有哪些步驟與決策點？">
    把現有的人工流程畫出來，找出每一個步驟與每一個需要判斷的決策點。

    ```text
    新客戶詢問 email 到達
      → 業務確認客戶來自哪個產業（判斷）
        → 到共用資料夾找對應的產品規格文件（查找）
          → 確認當前庫存與報價（查詢系統）
            → 起草回覆（撰寫）
              → 主管審核（人工）
                → 發送（執行）
    ```

    決策點越多、查找步驟越多，AI 工作流能創造的價值越大。
  </Step>
  <Step title="需要哪些資料來源？">
    列出這個任務需要存取的所有資料：

    <CardGroup cols={3}>
      <Card title="內部文件" icon="file-lines">
        產品規格 PDF、政策手冊、操作指南、常見問題庫
      </Card>

      <Card title="結構化資料" icon="table">
        庫存試算表、CRM 資料庫、ERP 系統、專案追蹤看板
      </Card>

      <Card title="非結構化資料" icon="messages">
        歷史 email、會議記錄、Slack 對話、客戶反饋
      </Card>
    </CardGroup>

    對每個資料來源，評估：**存取方式**（API / 直接連線 / 手動上傳）、**更新頻率**（即時 / 每日同步 / 靜態）、**敏感度**（公開 / 內部 / 機密）。
  </Step>
  <Step title="哪些步驟適合 LLM，哪些應由程式執行？">
    這是最容易做錯的設計決策。並非所有步驟都需要 LLM：

    | 適合 LLM 的工作 | 適合確定性程式碼的工作 |
    | --- | --- |
    | 理解自然語言意圖 | 從資料庫撈取特定記錄 |
    | 生成摘要與草稿 | 計算數字（總金額、百分比） |
    | 從非結構文字提取資訊 | 驗證 email 格式 |
    | 判斷情境與路由 | 發送通知、更新狀態 |
    | 處理模糊或開放性問題 | 格式轉換（日期、貨幣） |

    **原則：讓程式碼做程式碼最擅長的事，讓 LLM 做語言理解與生成。** 用 LLM 做加法運算是浪費，用正則表達式理解使用者意圖是妄想。
  </Step>
  <Step title="哪些資料或動作屬於高風險？">
    明確標出工作流中需要特別謹慎的部分：

    - **寫入風險**：工作流會不會修改資料庫、發送 email、建立訂單？這些動作需要人工確認關卡。
    - **資料敏感度**：哪些資料不能傳給外部 LLM API？需要在本地處理或脫敏後再送出。
    - **錯誤影響範圍**：如果 AI 判斷錯誤，最壞的情況是什麼？能回滾嗎？

    ```text
    低風險：生成草稿供人工審閱
    中風險：自動發送通知 email
    高風險：直接修改 ERP 訂單資料
    ```

    對高風險動作，建議加入「人在迴路（Human-in-the-Loop）」設計，讓 Agent 生成建議但由人確認執行。
  </Step>
  <Step title="如何判斷答案正確與任務完成？">
    這是許多 AI 專案忽略的關鍵問題。沒有評估機制，就無法知道系統是否真的在正確工作。

    設計評估標準：

    ```python
    # 範例：建立評估資料集
    EVALUATION_CASES = [
        {
            "input": "差旅費報銷上限是多少？",
            "expected_source": "travel_policy_2024.pdf",
            "expected_contains": ["每日", "住宿", "交通"],
            "should_not_contain": ["我不知道", "無法回答"]
        },
        {
            "input": "目前 Q4 的銷售數字是多少？",
            "expected_tool_called": "query_spreadsheet",
            "expected_context_type": "TOOL_USE"
        }
    ]
    ```

    至少建立 20–30 個典型問題的評估資料集，每次改動模型或 Prompt 後都能快速驗證是否退步。
  </Step>
  <Step title="發生錯誤時，使用者可以採取什麼行動？">
    每種可能的錯誤狀況，都應該有明確的使用者行動路徑：

    | 錯誤情境 | 使用者可採取的行動 |
    | --- | --- |
    | 找不到相關文件 | 確認 PDF 是否已上傳，或重新描述問題 |
    | 模型回答不確定 | 提供更具體的問題範圍 |
    | 工具連線失敗 | 直接前往來源系統查詢，系統提供直連連結 |
    | 任務超時 | 拆解成較小的子任務，或切換到非同步模式 |
  </Step>
</Steps>

## 從觀念篇走向 Data Machi 實作篇

這 30 天的主要成果，是建立一張完整的企業 AI 工作流知識地圖：你已經知道 RAG、Tool Use、Agent、LangGraph、可靠性與產品化各自解決什麼問題。下一階段不需要再依照 Day 31、Day 32 的形式延伸，而是改用連續專案的方式，把這些概念逐步實作到同一個 Data Machi 系統中。

```text
30 天觀念篇
回答「為什麼要這樣設計」
        ↓
Data Machi 實作篇
回答「如何把它真正做出來」
        ↓
進階工程篇
回答「正式上線後如何維護、評估與擴充」
```

實作篇會依照產品建構順序安排，而不是重新照觀念篇的順序走一次。每一篇都應對應一個可以執行、可以驗證的專案狀態，讓讀者逐步建立工具、State、Router、跨來源工作流、查核循環與部署能力。

## Data Machi 的下一步

完成了 Level 5 的核心工作流後，Data Machi 的路線圖上有幾個值得探索的方向：

<CardGroup cols={2}>
  <Card title="LangGraph Checkpointer" icon="floppy-disk">
    實作真正的任務中斷與恢復（interrupt/resume），讓長時間任務可以在伺服器重啟後繼續，而非從頭開始。
  </Card>

  <Card title="角色式審核 Agent" icon="users">
    設計多角色的 Agent 協作流程，例如「起草 Agent \+ 審核 Agent」的雙重驗證架構，提升輸出品質。
  </Card>

  <Card title="資料權限分層" icon="lock">
    根據使用者角色動態限制可查詢的知識庫範圍，確保敏感資料只對有權限的人可見。
  </Card>

  <Card title="Evaluation Dataset" icon="chart-bar">
    建立完整的評估資料集與自動化評估流程，讓每次 Prompt 或模型更新都有量化的品質基準。
  </Card>
</CardGroup>

<Tip>
  每一項新能力都應回到真實的工作需求來評估：**這個功能能解決哪個真實痛點？沒有它，使用者的工作受到什麼阻礙？** 不要為了追逐「Agent」這個名詞而堆砌功能。
</Tip>

## 30 天的核心轉變

回顧這 30 天，最重要的認知轉變不是學會了哪些框架，而是一種思維方式的改變：

<CardGroup cols={1}>
  <Card title="從「讓模型幫我寫一段話」到「設計可執行的工作流」" icon="arrow-right">
    企業 AI 最重要的進化，是從把 LLM 當成「寫作工具」，轉變成把工作流程拆解成「可取得資料、可執行、可驗證、可追蹤」的系統設計。

    模型只是這個系統中的一個組件——儘管是非常重要的組件，但它的價值必須透過整個系統架構才能發揮。
  </Card>
</CardGroup>

## 最後的提醒

<Info>
  30 天最重要的一句話：不要只打造會回答的 AI，而要打造能可靠推動工作向前的系統。

  一個好的企業知識工作流 Agent，使用者甚至不需要感謝 AI——他們只是覺得工作變得更順暢了、資訊更好找了、任務更少被遺漏了。這種「感覺不到科技存在」的體驗，才是企業 AI 工作流的最高成就。
</Info>
