一個 Agent 在本機能正確回答，不代表它已經適合企業使用。本機環境缺乏真實的多使用者負載、沒有資料隔離的壓力、憑證可以隨意放在設定檔，出錯了重啟一下就好。但正式上線代表的是：真實使用者的資料、真實的安全攻擊面、真實的服務可用性要求。這篇整理企業 Agent 上線前，每個團隊都應該系統性處理的四大面向。

## 一、憑證安全：第一道防線

<Warning>
  API Key 一旦進入 Git 歷史，即使後來刪除了那一行程式碼，只要有人能存取 git log，就能還原出那把金鑰。必須視為已暴露，並立即旋轉（Rotate）所有相關憑證。
</Warning>

### 憑證管理的基本守則

<Steps>
  <Step title="永不硬編碼（No Hardcoding）">
    所有 API Key、Service Account 憑證、資料庫密碼都必須透過環境變數或 Secret Manager 提供，絕不寫入程式碼。

    ```python
    # ❌ 錯誤：憑證硬寫在程式碼中
    OPENAI_API_KEY = "sk-proj-abc123..."

    # ✅ 正確：從環境變數讀取
    import os
    OPENAI_API_KEY = os.environ.get("OPENAI_API_KEY")
    if not OPENAI_API_KEY:
        raise EnvironmentError("OPENAI_API_KEY 未設定，請確認環境變數配置。")
    ```
  </Step>

  <Step title="加入 .gitignore 防護">
    確保所有含有憑證的設定檔都在 `.gitignore` 中列出：

    ```gitignore
    # 環境變數檔
    .env
    .env.local
    .env.production

    # 服務憑證
    **/service-account.json
    **/credentials.json
    **/*.pem
    **/*.key
    ```
  </Step>

  <Step title="使用 Secret Manager 管理生產環境憑證">
    正式環境建議採用雲端 Secret Manager（AWS Secrets Manager、GCP Secret Manager、Azure Key Vault），並設定：

    - **最小權限原則**：每個服務只能存取自己需要的 Secret
    - **定期輪換**：設定自動旋轉排程
    - **存取稽核**：記錄每一次 Secret 讀取操作

    ```yaml
    # Render 部署範例：透過環境變數注入憑證
    services:
      - type: web
        name: my-agent-backend
        env: python
        envVars:
          - key: OPENAI_API_KEY
            sync: false   # 在 Dashboard 手動設定，不存入 repo
          - key: GROQ_API_KEY
            sync: false
          - key: DATABASE_URL
            fromDatabase:
              name: my-agent-db
              property: connectionString
    ```
  </Step>
</Steps>

### 其他安全攻擊面

<CardGroup cols={2}>
  <Card title="跨網域設定（CORS）" icon="globe">
    CORS 不應設定為 `*`（允許所有來源）。正式環境必須明確列出允許的 Origin，並驗證所有跨域請求的 Token。
  </Card>
  <Card title="輸入驗證" icon="shield">
    LLM 的 Prompt Injection 是真實威脅。使用者輸入在送入 LLM 前，應進行長度限制、特殊字元過濾，避免惡意指令覆蓋系統 Prompt。
  </Card>
  <Card title="錯誤訊息不暴露內部資訊" icon="eye-slash">
    錯誤回應不應包含 stack trace、資料庫結構、API 路由或內部 IP 位址。對外錯誤訊息應是人類可讀的摘要。
  </Card>
  <Card title="資料傳輸加密" icon="lock">
    所有 API 通訊必須使用 HTTPS。若有自架服務，需確認 TLS 憑證有效期並設定自動更新。
  </Card>
</CardGroup>

## 二、測試策略：超越人工聊天測試

人工手動聊天不能作為唯一的測試手段。Agent 系統需要系統化的測試覆蓋，涵蓋多個層次：

<Accordion title="Smoke Tests：確認基本功能不壞掉">
  每次部署後自動執行的最基本健康檢查，驗證系統核心路徑是否正常：

  ```python
  import pytest
  import httpx

  BASE_URL = "http://localhost:8000"

  @pytest.mark.asyncio
  async def test_health_check():
      async with httpx.AsyncClient() as client:
          response = await client.get(f"{BASE_URL}/health")
      assert response.status_code == 200

  @pytest.mark.asyncio
  async def test_chat_endpoint_responds():
      async with httpx.AsyncClient(timeout=30) as client:
          response = await client.post(
              f"{BASE_URL}/api/chat",
              json={"message": "你好", "session_id": "smoke-test-001"}
          )
      assert response.status_code == 200
      data = response.json()
      assert "content" in data
      assert len(data["content"]) > 0
  ```
</Accordion>

<Accordion title="路由與工具呼叫測試">
  驗證 Agent 的上下文路由是否正確判斷，以及工具是否在預期情境下被呼叫：

  ```python
  @pytest.mark.asyncio
  async def test_pdf_query_triggers_rag_tool():
      """提問知識庫相關問題時，應呼叫 PDF 搜尋工具"""
      result = await agent.process("請問我們的差旅費報銷規定是什麼？")
      assert result.tools_called is not None
      assert "search_pdf" in result.tools_called
      assert result.context_type == "RAG"

  @pytest.mark.asyncio
  async def test_general_question_no_tool_call():
      """一般問候不應觸發任何工具呼叫"""
      result = await agent.process("今天天氣如何？")
      assert len(result.tools_called) == 0
      assert result.context_type == "GENERAL"
  ```
</Accordion>

<Accordion title="Schema 穩定性測試">
  驗證結構化輸出（會議記錄 JSON、行動項目等）的格式是否符合預期：

  ```python
  def test_meeting_notes_schema_stability():
      """驗證會議記錄輸出符合固定 schema"""
      sample_transcript = load_fixture("sample_meeting_transcript.txt")
      result = generate_meeting_notes(sample_transcript)

      # 必填欄位存在
      assert "executive_summary" in result
      assert "action_items" in result
      assert isinstance(result["action_items"], list)

      # action_items 結構正確
      for item in result["action_items"]:
          assert "task" in item
          assert "assignee" in item  # 可以是 null，但欄位必須存在
          assert item.get("priority") in ["high", "medium", "low", None]
  ```
</Accordion>

<Accordion title="前端 CI 流程">
  前端應加入自動化 lint、型別檢查與 production build，確保每次改動不破壞介面：

  ```yaml
  # GitHub Actions 範例
  name: Frontend CI

  on: [push, pull_request]

  jobs:
    lint-and-build:
      runs-on: ubuntu-latest
      steps:
        - uses: actions/checkout@v4
        - uses: actions/setup-node@v4
          with:
            node-version: '20'
        - run: npm ci
        - run: npm run lint
        - run: npm run type-check
        - run: npm run build
  ```
</Accordion>

## 三、Debug 面板與可觀測性

<Note>
  **可觀測性（Observability）** 是指系統能夠讓開發者在不修改程式碼的情況下，理解任意時刻的內部狀態。對 Agent 系統而言，這比一般應用程式更加重要，因為 LLM 的行為本身就是不確定性的。
</Note>

Data Machi 實作了一個僅在開發環境顯示的 Debug 面板，記錄每一輪對話的完整執行細節：

```typescript
interface DebugTrace {
  sessionId: string;
  turn: number;
  timestamp: string;
  contextDecision: {
    type: "RAG" | "TOOL" | "GENERAL" | "CLARIFY";
    reasoning: string;
    confidence: number;
  };
  toolsCalled: Array<{
    name: string;
    input: Record<string, unknown>;
    output: string;
    latencyMs: number;
  }>;
  llmCalls: Array<{
    model: string;
    promptTokens: number;
    completionTokens: number;
    latencyMs: number;
    cost: number;
  }>;
  totalLatencyMs: number;
  totalCost: number;
}
```

在正式環境，這些資訊應寫入結構化日誌（Structured Logs）供後台查詢，但不顯示給使用者。

## 四、部署架構與資料持久化

### 前後端分離部署

```text
前端（Next.js）→ Vercel
後端（FastAPI）→ Render / Railway / Fly.io
資料庫（PostgreSQL）→ Supabase / Railway / 雲端 RDS
向量資料庫（FAISS / Chroma / pgvector）→ 持久化掛載磁碟
```

<Warning>
  **暫存磁碟不等於持久儲存。** Render、Railway 等服務在每次部署或重啟後，暫存磁碟上的資料都會消失。對話歷史、PDF 索引、會議記錄若只存在暫存磁碟，重啟後使用者的所有資料都會不見。正式環境必須明確設計持久化策略。
</Warning>

### 資料持久化策略

| 資料類型 | 建議儲存方式 |
| --- | --- |
| 對話歷史 | PostgreSQL（關聯式資料庫） |
| PDF 原始檔案 | Object Storage（S3 / GCS / R2） |
| 向量索引 | pgvector 或持久化磁碟掛載 |
| 會議記錄 | PostgreSQL |
| Session Token | Redis 或資料庫 |
| 使用者設定 | PostgreSQL |

企業 Agent 的可信度，來自模型之外的大量工程紀律。一個在 Demo 中令人驚豔的 Agent，和一個在企業正式環境中值得信任的產品，中間的距離就是這篇所整理的這些看似枯燥但不可或缺的工作。
