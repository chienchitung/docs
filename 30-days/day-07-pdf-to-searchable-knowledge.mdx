你把一份 PDF 上傳到系統，這份文件就自動變成 AI 能理解的知識了嗎？答案是：還差得遠。一份 PDF 在系統眼裡，起初不過是一堆字元與排版指令的集合——它既不知道哪些段落重要，也不懂得回答問題。要讓 AI 真正能「讀懂」並「搜尋」這份文件，中間至少要經過四個關鍵步驟：**解析（Parse）、切割（Chunk）、向量化（Embed）與建立索引（Index）**。每一個步驟的品質，都直接影響最終 RAG 系統的搜尋準確度。

## 從文件到知識庫的完整流程

<Steps>
  <Step title="解析（Parse）：讀取文字與結構">
    系統首先讀取 PDF 的文字內容、頁碼與基本結構資訊。對於有完整文字層的 PDF（例如從 Word 轉出的數位 PDF），這一步相對直接；對於掃描文件或含有大量圖表的 PDF，則需要 OCR 或多模態處理（這部分我們會在 Day 09 詳細說明）。

    這一步的核心目標：把 PDF 的「外殼」打開，取出可以被後續處理的純文字內容。
  </Step>
  <Step title="切割（Chunking）：把長文件切成小片段">
    整份文件不會直接交給模型。系統會依照設定的大小與重疊規則，把長文本切成一段段的 Chunk。每個 Chunk 都是後續搜尋與生成的基本單位。

    切割策略直接影響搜尋品質：切太大，搜尋時回傳的內容過於冗長，干擾模型判斷；切太小，前後文脈絡可能被破壞，模型看到的只是片段資訊。
  </Step>
  <Step title="向量化（Embedding）：把文字轉成語意數字">
    每個 Chunk 會透過 Embedding 模型，轉換成一組高維度的數字向量。這組向量能夠代表該段落的「語意」——意思相近的段落，在向量空間中的距離也會相近。

    這是語意搜尋得以實現的核心技術基礎。
  </Step>
  <Step title="建立索引（Indexing）：存進向量資料庫">
    所有向量連同對應的元資料（文件名稱、頁碼、Chunk 編號、原始文字），一起存入向量資料庫（如 FAISS、Pinecone、Qdrant 等）。索引建好後，系統就能在毫秒內完成語意相似度比對。

    當使用者提問時，問題同樣會被轉成向量，再與索引中所有 Chunk 的向量比對，找出語意最近的若干片段，作為模型的參考資料。
  </Step>
</Steps>

## 為什麼切割（Chunking）這麼重要？

Chunking 是整個知識庫建置過程中最容易被低估的步驟，也是影響搜尋效果最大的環節之一。

<CardGroup cols={2}>
  <Card title="切太大的問題" icon="expand">
    每次查詢都回傳大量文字，其中可能只有一小部分真正相關。大量無關內容會稀釋重點，讓模型在回答時容易混淆，也增加 Token 成本。
  </Card>
  <Card title="切太小的問題" icon="compress">
    單一 Chunk 只剩下幾句話，缺乏足夠的上下文。模型可能看到一個結論，卻看不到支撐這個結論的前提，導致答案片面甚至錯誤。
  </Card>
</CardGroup>

### 固定大小切割 + 重疊區段

Data Machi 目前使用「固定大小切割 + 重疊區段」的策略。設定一個固定的 Chunk 大小（例如 512 tokens），並讓相鄰 Chunk 之間有一段重疊（例如 50 tokens）。

```text
原始段落（示意）：
[...前文...] | [Chunk A: tokens 1–512] | [Chunk B: tokens 463–974] | [後文...]
                              ↑ 重疊區段（tokens 463–512）

重疊的好處：
- Chunk A 的結尾資訊，也出現在 Chunk B 的開頭
- 跨 Chunk 的概念不會被完全切斷
- 搜尋命中任一 Chunk，上下文都保有足夠的連貫性
```

<Note>
  沒有一個「完美」的 Chunk 大小適用於所有場景。法律合約可能需要較大的 Chunk 保留完整條款語境；FAQ 文件則可能適合小 Chunk 讓每個問答對獨立存在。實際部署時需要根據文件類型與查詢模式進行調整。
</Note>

## Data Machi 實戰：知識庫的元資料設計

Data Machi 在建立知識庫時，不只存放文字向量，還會保存完整的元資料，讓搜尋結果可以追溯到具體來源。

```json
{
  "doc_id": "travel_policy_v3",
  "source": "差旅管理辦法_v3.pdf",
  "page": 3,
  "chunk_index": 7,
  "content_type": "text",
  "text": "出差申請應於出發日前五個工作天提出，並附上行程規劃與預算估算……"
}
```

這份元資料讓系統在回傳搜尋結果時，可以同時告訴模型：「這段話來自哪份文件的第幾頁」，讓最終答案具有完整的引用來源。

### FAISS 索引快取機制

系統會將 FAISS 向量索引序列化存到磁碟。重新啟動服務時，若偵測到文件內容沒有變更，就直接載入快取索引，不需要重新對所有 Chunk 做 Embedding。

```text
首次建立知識庫：
PDF → Parse → Chunk → Embed（呼叫 API，有成本）→ 存入 FAISS → 序列化到磁碟

重啟服務後（文件未變更）：
從磁碟載入 FAISS 索引 → 直接可用（不需重新 Embed）
```

<Tip>
  在文件量大的企業場景中，Embedding API 的費用可能相當可觀。快取機制能顯著降低重複計算的成本，也加速系統啟動速度。
</Tip>

## 知識庫維運的三個關鍵問題

建立知識庫只是開始，維運才是長期挑戰。

<Accordion title="文件更新後，如何重建索引？">
  當某份 PDF 有新版本時，需要先從索引中移除舊版本的所有 Chunk，再重新解析、切割與向量化新版本文件。如果不清除舊索引，新舊版本的內容可能同時出現在搜尋結果中，導致模型回答出現矛盾。

  設計上建議為每份文件使用唯一 ID，並在更新時執行「先刪後建」的策略，確保索引的一致性。
</Accordion>

<Accordion title="文件刪除後，如何清理向量？">
  向量資料庫不像關聯式資料庫那樣容易批次刪除。部分向量資料庫支援依 metadata filter 刪除；使用 FAISS 等靜態索引時，則通常需要重建整個索引。這是在選擇向量資料庫時需要考慮的維運成本。
</Accordion>

<Accordion title="重新部署後，資料還在嗎？">
  在容器化部署環境（如 Docker、Kubernetes）中，如果向量索引只存在記憶體或容器臨時空間，重啟後資料會消失。應確保索引檔案掛載到持久化存儲，或使用雲端向量資料庫服務，避免每次部署都需要重建索引。
</Accordion>

</Info>
