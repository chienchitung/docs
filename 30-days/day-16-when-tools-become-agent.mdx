在 AI 系統的設計中，「工具呼叫」與「Agent」經常被混用，但兩者在架構上有本質的差異。一個工具只負責執行特定能力，例如查詢試算表、搜尋文件、建立任務卡片。Agent 則需要根據任務情境主動判斷：要不要使用工具？使用哪一個？取得結果之後，下一步該做什麼？這個「判斷→行動→觀察→再判斷」的循環，才是 Agent 真正的核心所在。

## Tool 與 Agent 的根本差異

工具與 Agent 的邊界，往往不在技術實作，而在決策能力是否存在。

<CardGroup cols={2}>
  <Card title="🔧 Tool（工具）" icon="wrench">
    被呼叫時執行固定能力，不會自行判斷是否呼叫自己、何時停止，或是否需要換用其他工具。執行結束即完成任務。
  </Card>
  <Card title="🤖 Agent（代理）" icon="robot">
    接收到任務後，根據語意選擇工具、觀察執行結果、判斷是否足夠，必要時調整策略、重新行動，直到達成目標或觸發停止條件。
  </Card>
</CardGroup>

<Info>
  **核心差別是決策循環**：如果系統固定規定「收到問題就查 PDF」，這是一條自動化流程。當模型能根據問題選擇 PDF、試算表、Trello 或 Confluence，並在結果不足時主動改變策略，就開始具備 Agent 的特徵。
</Info>

## 決策循環長什麼樣子？

理解 Agent 的最好方式，是把它拆解成一個持續運作的判斷迴圈：

<Steps>
  <Step title="接收任務">
    使用者輸入問題或需求，Agent 理解意圖，判斷當前對話脈絡。
  </Step>
  <Step title="選擇工具">
    根據問題語意，從可用工具清單中選擇最適合的一個或多個工具。
  </Step>
  <Step title="執行並觀察">
    呼叫工具、取得執行結果，仔細觀察結果是否符合預期、資料是否完整。
  </Step>
  <Step title="重新判斷">
    若結果充分，整理並產生答案；若不足，調整策略、補查其他工具，或向使用者釐清需求。
  </Step>
  <Step title="輸出或繼續">
    產生最終回應，或在下一輪對話中延續此循環。
  </Step>
</Steps>

這個循環的存在，才是讓系統從「自動化腳本」演進到「智慧代理」的關鍵。

## 一個具體情境對比

讓我們用同一個情境，比較工具呼叫與 Agent 的差異：

**情境：使用者問「上個月哪個市場表現最好？」**

```text
# 工具呼叫模式（固定流程）
用戶輸入 → 呼叫 Google Sheets 工具 → 回傳原始資料 → 結束
（若資料不完整或欄位名稱不對，系統無法自行修正）

# Agent 模式（決策循環）
用戶輸入
  → 判斷需要數據分析工具
  → 呼叫 Google Sheets 查詢上個月銷售資料
  → 觀察：資料存在，但缺少「市場」欄位
  → 重新判斷：改查 Confluence 的區域定義文件
  → 整合兩份資料，產生完整答案
  → 回覆使用者
```

同一個問題，Agent 能在中途發現資料不足，主動補查，而固定流程只能回傳原始結果或報錯。

## Data Machi 的實作方式

在 Data Machi 系統中，Coordinator 扮演 Agent 的核心角色。它會綁定所有可用工具，模型收到問題後可以輸出 Tool Call；工具執行結果會以 `ToolMessage` 的形式回到模型，讓它決定是要繼續查詢、整合資料，還是直接產生答案。

```python
# 簡化示意：Agent 節點的基本結構
def agent_node(state: AgentState) -> AgentState:
    messages = state["messages"]
    
    # 模型根據對話與工具定義，決定是否呼叫工具
    response = llm_with_tools.invoke(messages)
    
    # 若模型輸出 tool_calls，代表需要繼續執行工具
    # 若輸出純文字，代表已準備好回答
    return {"messages": [response]}

def action_node(state: AgentState) -> AgentState:
    tool_calls = state["messages"][-1].tool_calls
    results = []
    for call in tool_calls:
        result = execute_tool(call)
        results.append(ToolMessage(content=result, tool_call_id=call["id"]))
    return {"messages": results}
```

這個 `agent → action → agent` 的循環，正是 ReAct 架構的基礎（我們將在 Day 17 深入探討）。

## 什麼時候真的需要 Agent？

Agent 架構不是萬靈丹，也帶來額外的複雜度與成本。在決定是否引入 Agent 之前，可以用這幾個問題來評估：

<Accordion title="任務步驟是否固定？">
  如果輸入格式固定、處理步驟明確、輸出格式一致，傳統程式流程通常更穩定、更快速、更易於維護。Agent 帶來的彈性，在這裡可能反而是麻煩。
</Accordion>

<Accordion title="工具選擇是否需要語意判斷？">
  當使用者的問題可能需要不同的工具組合，而這個組合取決於問題的語意內容（而非關鍵字比對），這才是 Agent 擅長的領域。
</Accordion>

<Accordion title="資料不足時需要動態調整嗎？">
  如果系統需要在「查無資料」「結果不完整」「來源衝突」等情況下自行決定下一步，Agent 的觀察-判斷能力就非常關鍵。
</Accordion>

<Accordion title="任務跨越多個資料來源嗎？">
  需要整合多個工具結果、比較不同來源、或在多個系統之間協調的任務，特別適合 Agent 架構。
</Accordion>

<Warning>
  不要把「呼叫一次 API」包裝成 Agent。Agent 的重點不是名稱，而是是否存在「觀察結果、重新判斷、選擇下一步」的能力。徒具 Agent 名稱卻沒有決策循環的系統，只是讓程式碼更複雜的自動化腳本。
</Warning>

## Agent 的邊界與安全

<Note>
  Agent 並不代表 AI 擁有自由意志或無限制的決策能力。它只是被允許在預先定義的工具清單、業務規則與明確的停止條件中做出選擇。邊界設計是企業 Agent 的核心安全考量。
</Note>

一個設計良好的 Agent 應該具備：

- **有限的工具集**：只能呼叫被明確授權的工具
- **明確的停止條件**：達到答案或超過嘗試次數上限時終止
- **可觀測的行動記錄**：每一次工具呼叫都有完整的日誌
- **失敗時的優雅降級**：工具失敗時知道如何回報，而不是無限重試

<Info>
  今天只要記住一件事：Tool 提供能力，Agent 負責選擇與組合能力。
</Info>
