在企業 AI 工作流的設計過程中，RAG 與 Tool Use 是兩個最常被放在同一個句子裡討論的技術概念，卻也是最常被混為一談的兩件事。它們都是讓模型「取得外部資訊」的手段，但一個解決的是「知識在哪裡」，另一個解決的是「能做什麼事」——弄清楚這個差異，才能在設計系統時做出正確的決策。

## 從根本理解兩者的差異

RAG（Retrieval-Augmented Generation）的核心邏輯是：**先搜尋，再回答**。當使用者提出問題，系統會先從知識庫（文件、向量資料庫、PDF 等）檢索出最相關的段落，再把這些段落連同問題一起送給語言模型，讓它根據找到的內容生成答案。RAG 的重點是「把正確的知識片段找回來」，模型本身只負責最後的理解與表達。

Tool Use 則是另一條路線。模型在推理過程中判斷「我需要呼叫某個外部能力」，然後觸發一個工具——這個工具可能是查詢 Google Sheets 中的即時數字、讀取 Trello 上的最新任務狀態、在 Confluence 搜尋正式定義，也可以是寄送一封 Email、建立一張新卡片，或是執行一段計算程式。工具執行完成後，結果再回到模型，讓它繼續推理或回答。

<CardGroup cols={2}>
  <Card title="RAG：找知識" icon="magnifying-glass">
    從非結構化文件中檢索相關段落，適合「這件事的定義或背景是什麼」這類問題。知識是靜態的、預先嵌入好的。
  </Card>

  <Card title="Tool Use：做動作" icon="wrench">
    呼叫外部 API 或執行程式，適合「現在的數字是多少」或「幫我建立一筆資料」這類需要即時操作的問題。
  </Card>
</CardGroup>

## 用公司情境來理解

光看定義可能還是抽象，用一個實際的企業情境來對照會更清楚。

假設你是一家公司的數據分析師，新進同事問你：「Active Customer 的定義是什麼？」這個問題的答案是靜態知識，存在某份規格文件或 Confluence 頁面裡，RAG 是對的工具——從知識庫中找到定義，回傳給使用者。

但如果這位同事問的是「2026 年每個月的 Active Customer 數量是多少？」情況就完全不同了。這個問題需要讀取真實的資料表、執行篩選與計算、回傳精確數字。這不是在找知識，而是在操作一個資料系統——這是 Tool Use 的場景。

<Info>
  同一個詞彙（Active Customer）在兩個問題中扮演不同角色：一個是在問「定義」，一個是在問「數量」。前者靠 RAG，後者靠 Tool Use。搞清楚使用者的意圖，才能選對工具。
</Info>

實務上，這兩個能力往往需要同時存在。一個完整的問題可能是：「Active Customer 的定義是什麼，而且上個月的數字符合這個定義嗎？」這就需要先用 RAG 找到定義，再用 Tool Use 去資料表驗證數字是否吻合。

## Tool 的基本結構

每一個 Tool 通常由以下幾個部分組成：

<Steps>
  <Step title="名稱（Name）">
    清楚、簡短的識別名稱，讓模型在多個工具中能快速辨別。例如 `get_active_customers_by_month` 比 `query_data` 更有辨識度。
  </Step>
  <Step title="用途說明（Description）">
    這是最關鍵的部分。模型根據說明文字來判斷「什麼時候應該用這個工具」。說明太模糊，模型就容易誤用；說明太複雜，又增加解析負擔。
  </Step>
  <Step title="輸入參數（Parameters）">
    定義工具需要什麼輸入。例如查詢工單數量可能需要 `start_date`、`end_date`、`category` 等欄位，每個參數都應標注是否必填與格式說明。
  </Step>
  <Step title="回傳結果（Return Value）">
    工具執行後回傳給模型的資料。格式應一致且可預期，讓模型容易解讀。通常建議回傳結構化的 JSON，並附上必要的欄位說明。
  </Step>
</Steps>

模型不直接操作底層 API，而是「選擇」哪個 Tool 適合當前任務，再由程式層真正執行。這個設計讓模型專注在推理，而執行層可以獨立測試與維護。

```python
# 一個簡化的 Tool 定義範例（使用 LangChain 風格）
@tool
def get_active_customers_by_month(year: int, month: int) -> dict:
    """
    查詢指定年月的 Active Customer 數量。
    Active Customer 定義為當月內有至少一次登入記錄的使用者。
    回傳 {'year': int, 'month': int, 'count': int}
    """
    # 程式層負責實際執行
    df = load_customer_sheet()
    filtered = df[(df['year'] == year) & (df['month'] == month)]
    return {"year": year, "month": month, "count": len(filtered)}
```

## Data Machi 的工具設計方式

在 Data Machi 的架構中，Google Sheets、Trello、Confluence 與 PDF 搜尋被各自包裝成獨立的 Tool。這個設計的好處是：Coordinator（協調模型）可以用相對一致的方式選擇能力，而不必理解每個外部服務背後的 API 細節與認證邏輯。

<Accordion title="為什麼要把各種來源包裝成統一的 Tool 介面？">
  每個外部系統都有自己的 API 規格、認證方式與資料格式。如果讓模型直接面對這些差異，Prompt 會變得無比複雜，也很難維護。把每個來源包裝成 Tool 後，模型只需要知道「這個工具做什麼」，而不需要知道「它怎麼連線到哪個服務」。開發者也可以在不更換模型的情況下，更換底層 API 的實作。
</Accordion>

這個做法的另一個好處是可測試性：每個 Tool 都可以獨立測試，確認輸入輸出是否符合預期，不需要每次都跑完整的模型推理流程。

## 踩坑筆記

<Warning>
  **Tool 的說明文字非常重要，絕對不能隨便寫。** 描述太模糊（例如「查詢資料」）會讓模型在多個工具間猶豫不決，甚至選錯。工具太多且功能互相重疊，也會顯著增加模型的判斷難度，導致不穩定的行為。
</Warning>

設計 Tool 時，建議遵守以下原則：

- **每個 Tool 只做一件事**，邊界清楚，不要試圖設計一個「萬用查詢工具」
- **說明文字要描述適用場景**，而不只是功能本身。「當使用者詢問某月份的數量時使用此工具」比「查詢數量」更有用
- **回傳格式要一致**，讓模型在整合多個工具結果時不需要額外轉換
- **預期的錯誤也要處理**，例如找不到資料時應回傳明確的錯誤訊息，而不是空值或例外

<Info>
  今天只要記住一件事：RAG 是一種檢索能力，而 Tool Use 是讓 AI 接上外部世界的方法。
</Info>
