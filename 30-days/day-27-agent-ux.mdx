Agent 完成一個任務，背後可能需要理解問題意圖、呼叫多個工具、驗證答案、保存紀錄，甚至多輪反覆嘗試。即使最終答案完全正確，若使用者在整個過程中只能看著畫面空轉，很快就會認為系統壞掉了。Agent UX 的核心挑戰，是讓使用者在等待期間持續感知到「工作正在可靠地推進」。

## 為什麼 Agent UX 和一般 UX 不同？

傳統軟體的回應通常是即時的（點擊按鈕、資料出現），即使需要等待，進度也容易量化（上傳 40%、第 2 步共 5 步）。

Agent 的本質卻是非確定性的：
- 不知道需要呼叫幾個工具
- 不知道哪一輪 LLM 呼叫會耗時最長
- 任何一個中間步驟都可能失敗或需要重試
- 串流輸出結束不代表任務真正完成

這讓傳統的進度條設計幾乎無用武之地，需要全新的 UX 思維。

## 進度提示的設計原則

<Steps>
  <Step title="描述工作階段，而非技術細節">
    好的進度提示讓使用者看懂「現在在做什麼」，而不是暴露內部的工具 ID 或模型呼叫鏈。

    | ❌ 不建議顯示 | ✅ 建議顯示 |
    | --- | --- |
    | `tool_call: pdf_search_v2` | 「正在搜尋知識庫文件...」 |
    | `LLM routing decision: context=RAG` | 「確認問題範圍...」 |
    | `Error: 429 Too Many Requests` | 「模型目前負載較高，稍等一下...」 |
    | `validate_output: schema_check` | 「正在確認回答的準確性...」 |

    以 Data Machi 為例，每個工作階段對應一條人類可讀的進度訊息：

    ```typescript
    const PROGRESS_MESSAGES = {
      routing:    "確認問題範圍...",
      searching:  "搜尋相關文件...",
      querying:   "查詢工作表資料...",
      generating: "整理回答中...",
      validating: "確認資料準確性...",
      saving:     "保存對話紀錄...",
    };
    ```
  </Step>

  <Step title="串流要與任務完成同步">
    串流輸出（Streaming）能讓使用者更早看到文字，改善感知速度，但若處理不慎反而會造成困惑。

    **早期版本的問題：**

    ```text
    [前端] 文字開始串流顯示 ✓
    [後端] 仍在執行查核與資料庫存檔 ...
    [前端] 文字顯示完畢，輸入框仍被鎖住 ← 使用者困惑
    ```

    **改善後的設計：**

    ```text
    [後端] 完成生成 + 驗證 + 存檔 → 送出 final 事件
    [前端] 收到 final 事件 → 播放打字動畫 → 解鎖輸入框
    ```

    這樣使用者看到的「文字出現」與「可以繼續操作」是同步的，不會出現文字結束卻什麼都不能點的尷尬狀態。

    ```typescript
    // 前端監聽 SSE 事件
    eventSource.addEventListener('progress', (e) => {
      const { stage, message } = JSON.parse(e.data);
      updateProgressIndicator(stage, message);
    });

    eventSource.addEventListener('final', (e) => {
      const { content } = JSON.parse(e.data);
      // 用動畫播放最終回答，而非即時串流
      typewriterEffect(content);
      unlockInputField();
    });
    ```
  </Step>

  <Step title="錯誤訊息要可行動">
    「Something went wrong」是最無用的錯誤訊息。使用者需要知道：**發生了什麼事**，以及**可以做什麼**。

    <CardGroup cols={2}>
      <Card title="PDF 尚未建立索引" icon="file-pdf">
        「這份 PDF 尚未完成索引建立，請至知識庫頁面重新上傳後再試。」
      </Card>
      <Card title="模型過載" icon="server">
        「AI 模型目前負載較高，建議 30 秒後重新提問，或縮小問題範圍。」
      </Card>
      <Card title="找不到支持資料" icon="magnifying-glass">
        「未能在知識庫中找到足夠的相關資訊，建議確認資料是否已上傳。」
      </Card>
      <Card title="工具執行失敗" icon="wrench">
        「查詢工作表時發生錯誤，請確認試算表連線是否仍然有效。」
      </Card>
    </CardGroup>
  </Step>

  <Step title="完成狀態要明確">
    使用者需要知道任務**真的結束了**，而不是猜測。完成後應清楚顯示：

    - 回答已生成並顯示
    - 紀錄已保存（若有保存機制）
    - 輸入框已解鎖，可以繼續提問
    - 若有相關行動項目，提供快速入口

    ```typescript
    // 完成狀態的視覺反饋
    function onTaskComplete(result) {
      displayAnswer(result.content);
      showSavedIndicator();     // 顯示「已儲存」小標記
      unlockInputField();
      if (result.actionItems?.length > 0) {
        showActionItemsPrompt(result.actionItems);  // 提示有待辦事項
      }
    }
    ```
  </Step>
</Steps>

## 不要讓模型的「請稍等」成為最終回答

這是一個常見但危險的 UX 陷阱：

<Warning>
  如果模型在回答中輸出「請稍等，我幫你查一下相關資料...」，但系統並沒有真的在背景繼續執行任何工具，這句話就會成為最終回答，讓使用者以為 Agent 正在忙碌，卻永遠等不到結果。
</Warning>

正確的設計有兩種選擇：

1. **如果支援背景非同步執行**：在回應中說明任務已進入佇列，並提供狀態追蹤介面
2. **如果不支援非同步**：在同一輪對話中真正呼叫工具取得資料，或明確告知使用者「目前無法查詢，請您直接到 XXX 查看」

## Agent UX 成熟度對照

<Accordion title="Level 1：只有轉圈圈">
  使用者只看到一個 Loading 動畫，不知道現在在做什麼、還要等多久。任何延遲都會引發「是不是壞掉了？」的疑慮。這是最基本也最不可接受的 Agent UX。
</Accordion>

<Accordion title="Level 2：有進度文字，但是技術語言">
  顯示了進度，但文字是 `tool_call: search_pdf`、`context: RAG_PIPELINE` 這類工程術語。非技術使用者看不懂，反而增加困惑。
</Accordion>

<Accordion title="Level 3：人類可讀的進度訊息">
  進度提示改成「搜尋文件中...」「整理回答中...」等人類可讀語言。使用者能理解系統正在做什麼，信任感大幅提升。這是大多數企業 Agent 應達到的基線水準。
</Accordion>

<Accordion title="Level 4：錯誤訊息可行動 + 完成狀態明確">
  不只告訴使用者「什麼出錯了」，還提供「下一步可以做什麼」。完成後有明確的視覺反饋，並自動解鎖後續操作。
</Accordion>

<Accordion title="Level 5：任務進度可追蹤、可恢復">
  使用者可以在任務執行期間離開頁面，回來後看到任務狀態與結果。支援長時間非同步任務、背景執行與通知機制。這是企業級 Agent 的理想目標。
</Accordion>
