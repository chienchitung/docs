企業 AI 系統最危險的失敗，不是回答「我不知道」，而是用非常有自信的語氣，說出一個看起來合理但實際上錯誤的數字、日期或進度。這種失敗在報告場合中尤其致命，因為錯誤資訊一旦被引用，往往已經造成決策失誤才會被發現。真正可靠的企業 Agent，必須知道何時應該停下來問清楚，何時應該重新查核，以及如何設計一個從根本上讓幻覺無處生根的架構。

## 什麼是幻覺，為什麼會發生？

語言模型的幻覺（Hallucination）不是程式錯誤，而是模型的本質特性。模型的任務是「預測下一個最可能的 Token」，當它沒有足夠的真實資料支撐時，仍然會生成看起來流暢合理的內容——只是這些內容可能是憑空捏造的。

```text
# 幻覺的常見形式

數字捏造：
  「這個季度的轉換率是 23.7%」
  （資料庫中根本沒有這個數字）

日期錯誤：
  「這個功能在 2024 年 3 月上線」
  （實際上是 2024 年 8 月）

名稱混淆：
  「負責這個專案的是 Alex Chen」
  （混淆了兩個不同的專案負責人）

邏輯填補：
  「延遲是因為跨部門溝通問題」
  （紀錄中完全沒有提到原因，純屬推測）
```

<Warning>
  「可能是跨部門溝通造成延遲」這類句子讀起來合理，但如果工具查詢結果或工作記錄中沒有相關證據，這就是幻覺。分析可以提出假設，但必須清楚標記為「待驗證假設」，絕不能以事實陳述的方式呈現。
</Warning>

## 何時應該先釐清？

並非所有問題都可以直接執行，有些問題在執行前必須先向使用者確認關鍵條件，否則查詢的結果會是錯的。

<Steps>
  <Step title="識別模糊的必要條件">
    如果使用者說「幫我做分析報告」，但沒有指定：資料來源（哪個系統）、時間範圍（哪個月、哪個季度）、分析對象（哪個市場、哪個產品），系統缺乏執行所需的關鍵條件。
  </Step>
  <Step title="找出最關鍵的一個問題">
    釐清不是把所有未知條件都列出來問使用者。好的釐清策略是識別「如果這個條件錯了，一切都白費」的最關鍵問題，只問這一個。
  </Step>
  <Step title="用具體選項降低使用者負擔">
    與其問「你想要哪個時間範圍？」，不如說「你是指 2024 Q3（7 月到 9 月），還是最近 90 天？」具體選項比開放式問題更容易獲得精準答案。
  </Step>
</Steps>

```text
# 需要釐清的情境範例

使用者：「幫我整理最近的銷售狀況」
→ 模糊條件：「最近」是多久？「銷售狀況」是指哪個指標？
→ 釐清問題：「你是指本月（10 月）的整體銷售額，還是特定產品線？」

使用者：「查一下那個專案的進度」
→ 模糊條件：「那個專案」是哪一個？
→ 釐清問題：「你是指 Project Atlas 還是 Project Nova？」
```

## 何時不應該釐清？

釐清是工具，不是藉口。過度釐清會讓 Agent 變成一個讓人沮喪的問答機器。

<Note>
  **不需要釐清的情境**：當使用者只是延續前文的追問，並且問題中的指稱物在對話歷史中已經清楚，就不應該重新詢問已知條件。例如對話脈絡已確認是在討論亞太市場 Q3 資料，使用者說「整理成表格」，就不需要再問「你想整理哪個市場、哪個季度的資料」。
</Note>

```text
# 不需要釐清的情境範例

使用者（延續前文）：「整理成表格」
→ 不需要釐清，直接轉換現有資料格式

使用者（延續前文）：「換個說法解釋給非技術人員聽」
→ 不需要釐清，直接改寫現有回答的語氣

使用者（延續前文）：「加上百分比」
→ 不需要釐清，直接在現有數字上加計算
```

## 什麼是 Verification Request？

Verification Request 與一般的改寫或追問截然不同，它是使用者明確要求重新核對事實正確性的訊號。

<CardGroup cols={2}>
  <Card title="⚠️ Verification 訊號" icon="magnifying-glass">
    「你確定嗎？」「重新確認一下」「這個數字好像不對」「再查一次」「我剛更新了資料，重新看看」
  </Card>
  <Card title="✅ 正確的處理方式" icon="check">
    忽略先前的工具結果（可能已過時），重新呼叫原始工具，取得最新資料後與原始問題的預期對照，回報是否有差異。
  </Card>
</CardGroup>

```python
def handle_verification_request(state: AgentState) -> AgentState:
    """處理使用者的查核請求"""
    
    # 1. 標記先前的工具結果為「待驗證」
    state["tool_context_valid"] = False
    
    # 2. 記錄先前的結果，用於後續比對
    previous_result = state.get("prior_tool_context", {})
    
    # 3. 重新呼叫原始工具（不使用快取）
    new_result = force_fresh_tool_call(state)
    
    # 4. 比對新舊結果，回報差異
    if results_differ(previous_result, new_result):
        return format_diff_response(previous_result, new_result)
    else:
        return format_confirmed_response(new_result)
```

## 零幻覺架構的設計原則

零幻覺不是一句 Prompt 就能解決的問題，而是需要在架構層面系統性地設計。

<Steps>
  <Step title="所有事實都必須可追溯">
    數字、日期、人名、專案名稱、規定條文——所有具體事實都必須能追溯到特定的工具查詢結果。不能來自模型的「記憶」或「常識」。
  </Step>
  <Step title="找不到就說找不到">
    工具查詢無結果時，回覆必須明確說明「在指定的資料來源中找不到相關資料」，而不是用常識或推測填補空白。
  </Step>
  <Step title="跨來源都找不到，不能靠猜">
    當多個工具來源都查無結果時，不能用常識補全內部縮寫、專案代號或組織名稱。縮寫「ATL」可能是任何東西，沒有明確對照就不能假設。
  </Step>
  <Step title="假設要標記為假設">
    分析性的推論（如「可能的原因」「潛在風險」）可以出現，但必須清楚標記為「分析推論」或「待驗證假設」，與基於工具結果的事實陳述明確區隔。
  </Step>
</Steps>

<Info>
  Data Machi 的設計原則：數字、日期、名稱與規定，都必須能追溯到工具查詢結果。工具找不到時，回覆應明確說明資料不足；即使找不到，也不能用常識或推測補全內容。
</Info>

## 釐清與幻覺防護的對話範例

```text
# 情境：使用者問了一個條件不清楚的問題

使用者：「ATL 這個月的進度怎麼樣？」

❌ 幻覺式回答：
「ATL（Atlantic 市場開發計畫）本月進度良好，
目前完成率約 75%，主要里程碑已達標。」
（「ATL」是什麼完全靠猜測，數字是編造的）

✅ 正確處理：
「我在 Trello 和 Confluence 中都有找到名為 ATL 的項目：
1. ATL-2024：亞太物流改善計畫（負責人：Lisa Wang）
2. Atlantic Region Q4 Campaign（負責人：Mark Chen）

你想查詢的是哪一個？」
```

```text
# 情境：工具查詢無結果

使用者：「上週五的 Daily Standup 說了什麼？」

❌ 幻覺式回答：
「根據一般的 Daily Standup 慣例，會議討論了
各成員的進度更新和阻礙事項。」
（這是常識填補，不是事實）

✅ 正確處理：
「我在 Confluence 和 Notion 中搜尋了上週五（10/18）
的會議記錄，沒有找到相關紀錄。請問會議記錄是否
存放在其他位置，或者沒有留下書面記錄？」
```

## 釐清問題的設計技巧

<Accordion title="只問最關鍵的一個問題">
  當有多個未知條件時，思考哪一個條件是「如果搞錯了一切都白費」的最關鍵變數，只問這一個。一次問太多問題會讓使用者不耐煩，也可能讓對話失焦。
</Accordion>

<Accordion title="提供具體選項">
  「你想查哪個時間範圍？」不如「你是指上個月（9 月）還是這個季度（Q3）？」具體選項能大幅減少使用者的思考成本，也讓 Agent 更容易準確理解意圖。
</Accordion>

<Accordion title="說明為什麼需要釐清">
  「請問你是指哪個 ATL 專案？我找到了兩個同名項目。」比單純問「你說的 ATL 是什麼？」更透明，使用者也更能理解釐清的必要性。
</Accordion>

<Accordion title="釐清後立即行動">
  使用者回答釐清問題後，不要再次確認，直接執行查詢。「好的，我馬上查詢 ATL-2024 的本月進度。」比「好的，你是說 ATL-2024，對嗎？」更有效率。
</Accordion>

<Info>
  今天只要記住一件事：可靠的 Agent 不只知道如何回答，也知道何時應該停下來問與重新查。
</Info>
