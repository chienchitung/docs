很多人在建立 AI 系統的初期，會有一個直覺：只要把規則寫得夠清楚、夠詳細，模型就應該能按照規則完成任務。這個想法在簡單的情境下有效，但隨著業務複雜度增加，你會越來越清楚地看到它的極限。Prompt 可以告訴模型角色、任務與期待的行為，但它無法**保證**每一個步驟真的被執行。這篇文章要幫你理解 Prompt 與工作流程的本質差異，以及企業級 AI 系統為何需要更嚴格的設計。

## 一個看似合理卻暗藏問題的設計

假設你在 System Prompt 寫下這樣的指令：

```text
你是企業數據助理。當使用者提問時，請遵守以下規則：
1. 先查詢 Google Sheets 取得相關數據
2. 如果 Sheets 找不到，再查詢 Confluence 文件
3. 最終回答必須附上資料來源
4. 如果資料不足，請說明無法確認而非自行推測
```

這段 Prompt 看起來很完整，對吧？

但實際上會發生什麼：

- 模型**可能遵守**，也**可能直接**根據語言模式回答，完全跳過查詢步驟
- 它甚至可能先說「好的，我來查一下」，然後根本沒有呼叫任何工具就給出答案
- 當問題複雜到超過三個步驟時，模型可能只記住前兩條規則，後面的被忽略
- 每次對話的執行結果可能不一致——同樣的問題，有時查工具，有時不查

<Warning>
  **Prompt 描述的是「期待的行為」，不是「被保證的行為」。** 模型是機率性的系統，同一段指令在不同情境下可能產生不同的執行路徑，這對企業級應用來說是不可接受的。
</Warning>

## 四個不同的層次

理解企業 AI 系統設計，需要區分四個根本不同的概念：

<CardGroup cols={2}>
  <Card title="Prompt｜描述期待" icon="comment-dots">
    告訴模型它的角色、任務、輸出格式與行為偏好。這是「希望它怎麼做」的描述，但不能強制執行。
  </Card>
  <Card title="Policy｜定義邊界" icon="shield">
    定義系統不能違反的業務規則，例如「不能在沒有工具結果的情況下給出具體數字」。Policy 需要有程式層面的驗證，而不只是寫在 Prompt 裡。
  </Card>
  <Card title="Tool｜執行能力" icon="screwdriver-wrench">
    讓 AI 真正能夠讀取資料或執行操作的接口。沒有工具，Prompt 裡說的「去查詢資料」只是空話；有了工具，模型才能真正取得外部資訊。
  </Card>
  <Card title="Workflow｜控制流程" icon="diagram-project">
    用程式決定步驟順序、條件分支、錯誤重試與結束方式。這是讓整個系統具有可重複性與可預測性的核心機制。
  </Card>
</CardGroup>

<Note>
  這四個層次是疊加的，而不是替代的。好的企業 AI 系統需要同時擁有清晰的 Prompt、明確的 Policy、對應的 Tool，以及可靠的 Workflow。常見的錯誤是以為 Prompt 可以取代其他三個層次。
</Note>

## 什麼是真正的 Workflow？

Workflow 的核心是**程式層面的流程控制**，而不是文字說明。

以「回答需求工單趨勢問題」為例，一個真正的 Workflow 應該做到：

<Steps>
  <Step title="接收問題，判斷類型">
    程式判斷問題需要數據查詢、文件查詢，還是兩者都需要，並設定執行路徑。
  </Step>
  <Step title="呼叫工具，等待結果">
    程式發出工具呼叫請求，等待工具返回結果。**不允許在工具結果返回之前生成最終答案。**
  </Step>
  <Step title="驗證工具是否真的被呼叫">
    檢查模型的輸出中是否包含工具呼叫。如果模型只輸出等待語句（「好的，我來查一下」）卻沒有實際呼叫工具，工作流會**要求它重新執行**，而不是把這句話當成最終答案。
  </Step>
  <Step title="整合結果，生成回應">
    以工具返回的真實資料為基礎，生成回應。若工具未返回有效結果，則依 Policy 說明無法確認。
  </Step>
  <Step title="錯誤處理與結束條件">
    設定最大重試次數、超時處理與兜底回應，確保系統在任何情況下都有確定的結束行為，而不是無限等待。
  </Step>
</Steps>

## Data Machi 的實作設計

在 Data Machi 的開發過程中，我們把規則拆成不同的優先層級：

```text
L1 (Workflow)  → 程式強制執行：工具呼叫、步驟順序、結束條件
L2 (Policy)    → 系統驗證：查不到資料時的處理方式、來源引用規則
L3 (Prompt)    → 語氣偏好：回答格式、語言風格、說明詳細程度
```

程式會檢查模型是否真的發出了工具呼叫。若模型只輸出純文字（不論多像「正在查詢」），工作流會介入並要求模型重新執行正確步驟。

<Tip>
  一個實用的診斷方法：在你的 AI 系統中加入日誌，記錄每次對話中工具被呼叫的次數與時間。如果有很多對話顯示「零次工具呼叫」，代表模型經常在「直接回答」而非按流程執行。
</Tip>

## 小白版比喻

**Prompt** 像員工手冊：它寫著「報帳前請先取得主管簽核」。

**Workflow** 像報帳系統：當簽核欄空白時，按下送出會顯示錯誤，**系統不讓你通過**。

員工手冊可以被忽略；系統的阻擋機制無法繞過。

企業流程的可靠性，來自後者，而不是前者。

<Accordion title="為什麼隨著規則增加，Prompt 會越來越不可靠？">
  大型語言模型的注意力機制有其限制。當 System Prompt 包含大量規則時，模型更容易「遺忘」靠後的規則、在細節規則與整體目標之間產生衝突，或是在壓力情境下（例如問題很複雜）優先滿足表面期待而跳過程序要求。

  這不是模型的「壞意」，而是機率性系統的本質特徵。解決方法不是把 Prompt 寫得更長，而是把必須保證執行的規則，移到程式層面去實作。
</Accordion>

<Accordion title="Agentic Workflow 和一般自動化有什麼不同？">
  傳統自動化（例如 RPA）的每一個步驟都是確定性的：如果 A 則 B，否則 C。Agentic Workflow 允許 AI 在一定範圍內自主決定下一步：根據問題類型選擇工具、根據工具結果決定是否需要補充查詢。

  這帶來更強的彈性，但也帶來更高的不確定性。因此，好的 Agentic Workflow 設計需要在「允許 AI 自主決策」和「用程式保證關鍵行為」之間找到平衡。
</Accordion>

## 踩坑筆記

當規則越來越多時，不要只是把 Prompt 寫得更長。先判斷：

- **這條規則是語氣偏好？** → 放在 Prompt，允許模型有一定彈性
- **這條規則是業務必要？** → 用程式保證，不能靠模型「自覺遵守」

一個簡單的判斷標準：**如果這條規則被違反，會不會影響答案的正確性或可信度？** 如果會，就應該在程式層面強制執行。
