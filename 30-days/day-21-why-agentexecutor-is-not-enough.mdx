在 AI Agent 的早期探索階段，LangChain 的 `AgentExecutor` 是許多開發者的第一個起點。你只需要把問題、對話紀錄與工具清單交給模型，它就會自動在「決定呼叫工具」與「輸出最終答案」之間反覆循環，直到任務完成。這種方式確實讓人快速體驗到 Agent 的魅力，但當流程逐漸複雜、進入真實的企業環境時，`AgentExecutor` 的邊界也開始浮現——不是它不夠聰明，而是它的設計哲學讓開發者失去了對流程的精確控制權。

## 什麼是 AgentExecutor？

`AgentExecutor` 是 LangChain 提供的執行容器，負責協調 LLM 模型與工具之間的 ReAct 循環（Reasoning + Acting）。其核心邏輯非常直觀：

<Steps>
  <Step title="接收使用者輸入">
    將使用者問題、可用工具描述與對話歷史整合成一個 Prompt，送入 LLM。
  </Step>
  <Step title="模型決策">
    LLM 判斷目前應該呼叫哪個工具（附帶參數），或直接輸出最終答案。
  </Step>
  <Step title="工具執行">
    若模型選擇呼叫工具，`AgentExecutor` 執行對應工具並取得結果，將結果附加回對話。
  </Step>
  <Step title="反覆循環">
    把工具結果回饋給模型，繼續下一輪判斷，直到模型輸出最終答案或達到最大迭代次數。
  </Step>
</Steps>

這個模式在簡單場景下運作良好。但「簡單場景」和「企業流程」之間，有一段不小的距離。

## 黑箱循環的三個核心問題

當業務需求增加時，`AgentExecutor` 的本質限制就會一一出現。

<CardGroup cols={1}>
  <Card title="問題一：流程順序只能靠 Prompt 約束" icon="message-exclamation">
    若你需要模型先查詢資料庫、再彙整文件、最後格式化輸出，你唯一的手段是在 Prompt 裡寫「請先做 A，再做 B」。但 LLM 無法保證嚴格遵守這個順序——它可能跳步、合併步驟，或在某個中間環節提早輸出結論。當流程的正確性關係到業務結果時，這種不確定性是不可接受的。

    ```text
    ❌ Prompt 約束：「請先查詢 Sheets，再查 Confluence，最後彙整報告」
    ✅ 程式約束：step1 → step2 → step3，每步完成後才允許進入下一步
    ```
  </Card>
  <Card title="問題二：多 Agent 交接流程難以表達" icon="arrow-right-arrow-left">
    企業裡常見的審核流程是：Agent A 先搜尋並整理資料，Agent B 負責審核品質，若審核失敗則退回 Agent A 重新查詢。這種帶有條件分支與回退的拓撲結構，在 `AgentExecutor` 的單一循環模型裡幾乎無法自然表達——你必須在 Prompt 裡描述這個邏輯，並且祈禱模型能正確理解。
  </Card>
  <Card title="問題三：高風險操作前的人工暫停點難以實作" icon="hand">
    在寄出報告郵件、刪除文件或更新關鍵資料之前，企業流程通常需要一個人工確認步驟。`AgentExecutor` 的循環是連續的，它沒有內建的「暫停、等待人類批准、再恢復」機制。雖然可以用 Callback 或 Custom Chain 勉強模擬，但這會讓程式碼變得脆弱且難以維護。
  </Card>
</CardGroup>

## 為什麼企業特別在意可控性？

個人用的 AI 助理允許犯錯，因為代價低——最多是一個不理想的回答。但企業流程的情況截然不同：

<Warning>
  企業環境中，未經授權的操作可能導致資料遺失、錯誤通知發出、財務紀錄被覆蓋，乃至於觸犯合規規定。模型「覺得可以做」，和系統「被授權允許做」是兩件完全不同的事。
</Warning>

企業對 AI 系統的核心要求包括：

- **明確責任**：每一個動作必須能追溯到明確的觸發條件與授權節點
- **權限邊界**：不同角色、不同情境下的操作範圍必須由程式控制，而非模型自行判斷
- **稽核紀錄**：高風險操作必須留下可查核的執行紀錄
- **可預期行為**：相同輸入應產生相同的流程路徑，不能每次執行都有不同的「創意解法」

這些需求都指向同一個結論：企業需要的不只是一個聰明的模型，而是**可預期的流程控制**。

## Data Machi 的演進歷程

Data Machi 在早期版本中同樣依賴 `AgentExecutor` 驅動查詢流程。對於「查一個問題、呼叫一個工具、返回答案」這類簡單場景，它運作得相當順暢。但隨著業務需求增加——需要同時查詢多個系統、需要根據查詢結果決定下一步、需要在關鍵節點暫停等待確認——我們逐漸感受到黑箱循環的摩擦。

最終，我們把核心流程遷移到 LangGraph 的 `StateGraph`。這不是一次「換個更酷的框架」的決定，而是一次深思熟慮的架構選擇：把對流程的控制權，從模型的 Prompt 約束移回到程式邏輯本身。

<Accordion title="AgentExecutor 與 LangGraph 的定位比較">

| 維度 | AgentExecutor | LangGraph StateGraph |
|------|--------------|----------------------|
| 流程控制 | 由 LLM 透過 Prompt 決定 | 由開發者用 Node 與 Edge 定義 |
| 條件分支 | 模型自行判斷 | 程式層級的條件 Edge |
| 狀態保存 | 對話歷史（線性） | 結構化 State（可自訂欄位）|
| 人工介入 | 需要額外 Hack | 內建 interrupt/resume 支援 |
| 除錯難度 | 難（決策藏在模型內） | 較易（每個節點可單獨測試）|
| 適用場景 | 簡單、短流程 Agent | 複雜、多步驟、有審核需求的流程 |

</Accordion>

## 踩坑筆記：別過早抽象

<Note>
  簡單的問答場景不一定需要 LangGraph。如果你的 Agent 只有 2–3 個工具、流程是單向的、沒有複雜的條件分支，`AgentExecutor` 或簡單的 LCEL chain 可能仍是最快的解法。架構應該隨著問題的複雜度與風險等級成長，而不是一開始就追求最完整的圖形結構。過早引入複雜架構，只會讓早期開發速度變慢，讓團隊在還沒理解問題本質之前就陷入框架細節。
</Note>

評估是否需要遷移到更複雜架構的幾個訊號：

- 你開始在 Prompt 裡寫大量「你必須先做 X 再做 Y」的指令
- 你的 Agent 有時跳過某個必要步驟，但你只能透過更多 Prompt 修補
- 你需要在流程中的某個點等待外部確認才能繼續
- 你需要記錄每個步驟的執行狀態以供稽核

<Info>
  今天只要記住一件事：當流程風險與複雜度提高，企業需要的不只是聰明模型，而是可預期的控制。
</Info>
