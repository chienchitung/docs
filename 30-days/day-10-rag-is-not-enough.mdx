學完 RAG 的運作原理之後，很容易產生一個過度樂觀的預期：「只要把所有企業資料放進知識庫，AI 就能回答所有問題、完成所有工作。」這個想法有一半是對的，另一半則是危險的誤解。RAG 確實讓 AI 能夠存取私有知識，但它本質上仍是一條單向管線——問題進來、資料找出來、答案生成——它不會主動判斷「我是否應該去查另一個系統」，也不會自然理解「這個任務是否已真正完成」。

## 一個真實場景：RAG 找到了，但還不夠

假設一位業務主管詢問 AI：

> 「我們的某項核心指標最近三個月持續下降，原因是什麼？相關的改善專案目前進行到哪裡了？」

這個看似單純的問題，其實跨越了多個資料來源：

<CardGroup cols={2}>
  <Card title="問題一：指標下降的原因" icon="chart-line-down">
    指標的定義與歷史趨勢分析可能在 **Confluence Wiki** 或 **PDF 報告**中；但最新的實際數字在 **Google Sheets** 或 **資料倉儲**裡。RAG 知識庫可以告訴你指標「應該」如何計算，但不能直接讀取昨天的數字。
  </Card>
  <Card title="問題二：專案的改善進度" icon="list-check">
    改善專案的狀態更新在 **Trello** 或 **Jira** 的看板裡，不是靜態文件。這需要即時查詢專案管理系統的 API，而非搜尋向量資料庫。
  </Card>
</CardGroup>

單一 RAG 知識庫無法自動代表所有資料來源。它回答的永遠只是「在我這份知識庫裡，關於這個主題有什麼？」——而不是「在整個企業的資訊系統中，這個問題的完整答案是什麼？」

## RAG 真正擅長的場景

清楚 RAG 的邊界，才能在正確的場景中發揮它的最大價值。RAG 非常適合以下類型的任務：

- **文件問答**：「差旅報銷規範允許搭乘商務艙的條件是什麼？」
- **規範查詢**：「根據員工手冊，試用期績效評核的流程為何？」
- **手冊摘要**：「把這份 50 頁的產品規格書的重點整理成一頁摘要。」
- **知識搜尋**：「公司歷史上有沒有處理過類似的客訴案例？」

這些任務的共同特點：**答案已經存在於靜態文件中，只需要找到並整理**。

## RAG 力不從心的場景

當任務的性質超出「搜尋靜態知識」時，RAG 就需要其他機制的配合：

<CardGroup cols={2}>
  <Card title="需要即時資料" icon="clock">
    股價、系統狀態、今日庫存量、昨天的銷售數字——這些不住在 PDF 裡，而在即時的 API 或資料庫中。需要 **Tool Use** 去呼叫對應的資料介面。
  </Card>
  <Card title="需要計算與推論" icon="calculator">
    「過去三季的平均成長率是多少？」不是問知識庫，而是需要從數字資料執行計算。RAG 找不到「計算結果」，因為那不是已存在的靜態內容。
  </Card>
  <Card title="需要跨來源查核" icon="code-branch">
    把 Confluence 的規範、Google Sheets 的實際數字、與 Trello 的執行狀態對照比較——這需要能夠協調多個工具的 **Agent** 層。
  </Card>
  <Card title="需要觸發後續操作" icon="bolt">
    「根據查到的規範，自動發送一封申請確認信」——這已超出資訊回答的範疇，需要能夠執行動作的工具（如 Email API）與判斷何時執行的 Agent。
  </Card>
</CardGroup>

## 重要觀念：RAG 可以是 Agent 的一項工具

這是整個 30 天課程中最重要的架構觀念之一，值得特別強調：

> **RAG 和 Agent 不是同一個層次的東西——RAG 可以是 Agent 手上的一項工具。**

<Steps>
  <Step title="Agent 接收任務">
    使用者提出一個複雜問題。Agent（協調者）分析這個任務需要哪些資訊、需要呼叫哪些工具。
  </Step>
  <Step title="Agent 決定是否使用 RAG">
    如果任務需要查詢靜態文件知識，Agent 呼叫 `search_document_base`（RAG 工具）；如果需要即時數據，呼叫資料 API；如果需要專案狀態，呼叫 Trello Tool。
  </Step>
  <Step title="Agent 評估結果是否足夠">
    取得 RAG 搜尋結果後，Agent 判斷這份資訊是否足以回答問題。如果不夠，可以換關鍵字重試、改查另一個來源，或向使用者索取更多資訊。
  </Step>
  <Step title="Agent 整合並行動">
    把所有工具的結果整合，生成最終答案，或依據結果觸發下一步的行動（例如：建立一張 Trello 卡片、發送通知）。
  </Step>
</Steps>

## Data Machi 實戰：兩層架構的設計哲學

在 Data Machi 的架構中，這兩個層次有清晰的職責分工：

```text
Coordinator（Agent 層）
    ↓ 分析任務
    ↓ 決定要呼叫哪些工具
    ├── search_document_base（RAG 工具）→ 回傳文件知識
    ├── query_google_sheets（資料工具）→ 回傳即時數字
    ├── search_confluence（Wiki 工具）→ 回傳規範文件
    └── get_trello_cards（專案工具）→ 回傳專案狀態
    ↓ 整合所有工具回傳的結果
    ↓ 生成最終答案
```

`search_document_base` 負責的是「去 PDF 知識庫找相關段落」這一件事；Coordinator 負責的是「理解整個問題、判斷要不要用 RAG、結果不夠時要換什麼策略」。**這兩層不應混為一談**，也不應該期待 RAG 層自己完成 Agent 層的工作。

## 踩坑筆記：不要把所有資料硬塞進同一個向量資料庫

<Warning>
  將所有企業資料——文件知識、結構化數字、專案狀態、使用者對話記錄——都塞進同一個向量資料庫，是一個看似方便、實則危險的設計。

  不同類型的資料有根本不同的需求：
  - **更新頻率**：文件可能一季更新一次；即時數據每秒都在變
  - **查詢方式**：結構化數據適合 SQL；文件適合語意搜尋
  - **權限需求**：財務數字需要嚴格的存取控制；一般規範文件可能全員可查
  - **準確性要求**：「去年營收是多少」需要精確數字；「公司文化是什麼」可以模糊搜尋

  強行混用會讓每種資料都無法以最適合的方式被查詢，最終降低整體系統的可靠性。
</Warning>

<Accordion title="補充：從 RAG 到 Agentic RAG 的演進">
  傳統 RAG 是一次性的管線：一個問題，搜尋一次，生成一個答案。

  **Agentic RAG** 讓 AI 能夠迭代地使用 RAG 工具：
  - 第一次搜尋結果不夠時，自動調整關鍵字重試
  - 發現需要不同類型的資料時，切換到其他工具
  - 主動評估答案的完整性，決定是否需要再補充資訊
  - 在多步驟任務中，把前一步的搜尋結果作為下一步查詢的基礎

  這是我們在後續章節會深入探討的進階架構。
</Accordion>

<Info>
  今天只要記住一件事：RAG 解決「去哪裡找知識」，但不完整解決「下一步該做什麼」——讓 AI 真正完成工作，需要 Agent 層的協調與判斷。
</Info>

從下一篇開始，我們會讓 AI 從「會讀文件」，進一步學會「使用企業工具」——不只是回答問題，而是真正執行任務。
