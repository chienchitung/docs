_圖 1｜關鍵字搜尋比對字面，語意搜尋理解真正意圖_

你搜尋「床墊回購」，但文件裡寫的是「replacement cycle」或「再次購買睡眠商品」——這種字面不同、意思卻相近的情況，在企業文件中極為常見。傳統關鍵字搜尋遇到這個問題會沉默地漏掉相關段落；語意搜尋則試圖理解「概念上的相似性」。理解這兩種搜尋方式的差異，是設計高品質 RAG 系統的重要基礎。

## 關鍵字搜尋：字面上的精確比對

傳統的關鍵字搜尋（也稱為詞彙搜尋或 BM25 搜尋）的運作邏輯很直白：**找出包含查詢字詞的文件**。系統不理解「語意」，只做字串層面的比對與排名。

```text
使用者查詢：「床墊回購」

關鍵字搜尋的比對邏輯：
✅ 命中：「……床墊回購率在第二季提升了 12%……」（包含「床墊」+「回購」）
❌ 漏掉：「……replacement cycle for sleep products shows 90-day pattern……」
❌ 漏掉：「……消費者再次購買睡眠商品的平均間隔為三個月……」
```

這種精確性在某些場景下是優點：當你要找的就是一個特定的詞彙、代碼或人名時，關鍵字搜尋的命中是可預期且可控的。

## 語意搜尋：概念空間的相似度比對

語意搜尋的核心是 **Embedding**：把文字轉換成高維向量，讓意思相近的文字在向量空間中靠得更近。搜尋時，問題和文件片段都被轉成向量，系統計算它們之間的「距離」（通常是餘弦相似度），距離越近代表語意越相關。

```text
向量空間示意（概念性）：

「床墊回購」
    ↕ 距離近（語意相近）
「sleep product replacement cycle」
    ↕ 距離近
「再次購買睡眠商品的間隔」
    ↕ 距離遠（語意不同）
「公司差旅報銷規範」
```

即使字詞完全不同，只要概念相近，語意搜尋就可能將它們找出來。這對於自然語言提問、同義詞豐富的領域，或中英文混用的企業文件場景，特別有價值。

## 兩者的適用場景比較

這不是「哪個更好」的問題，而是「哪個更適合這個任務」的問題。

<CardGroup cols={2}>
  <Card title="關鍵字搜尋更適合" icon="magnifying-glass">
    - 產品型號、SKU、合約編號等精確代碼
    - 人名、部門名稱、系統名稱
    - 法條號碼（例如「第 37 條第 2 項」）
    - 已知在文件中確切出現的詞彙
    - 需要高度可預期性與可控性的場景
  </Card>

  <Card title="語意搜尋更適合" icon="brain">
    - 自然語言描述的問題（「為什麼…」「如何…」）
    - 同義詞或近義詞豐富的領域
    - 中英文混用的企業環境
    - 使用者不確定文件中的確切用詞
    - 抽象概念的查詢（「風險管理流程」）
  </Card>
</CardGroup>

<Note>
  語意搜尋並非萬能。當使用者的查詢本身語意模糊，或 Embedding 模型對特定領域的理解不足（例如高度專業的法律或醫療術語），語意搜尋的表現可能不如預期。
</Note>

## Data Machi 實戰：不同來源，不同搜尋策略

Data Machi 對不同類型的知識來源採用不同的搜尋策略，因為文件知識庫與企業 Wiki 的結構本來就不相同。

### Document Tool：向量語意搜尋

PDF 知識庫使用向量相似度搜尋。當使用者詢問「公司的加班補休規定」，系統不是逐字比對，而是把問題轉成向量，找出語意最接近的文件段落。

```python
# 示意：Document Tool 的搜尋邏輯
def search_documents(query: str, top_k: int = 5):
    query_embedding = embed_model.encode(query)
    results = faiss_index.search(query_embedding, top_k)
    return [
        {
            "text": chunk["text"],
            "source": chunk["source"],
            "page": chunk["page"],
            "score": score
        }
        for chunk, score in results
    ]
```

### Confluence Tool：關鍵字優先，變體補強

企業 Wiki（Confluence）的內容通常有明確的標題與標籤結構，適合關鍵字搜尋。Data Machi 的 Confluence Tool 會先用原始關鍵字查詢，若結果不足，再嘗試去除空格、拆分詞語等變體查詢策略。

```text
原始查詢：「年度績效考核流程」

Confluence 搜尋策略：
第一輪：完整字串查詢 → 「年度績效考核流程」
第二輪（若無結果）：拆分詞語 → 「年度績效」OR「績效考核」OR「考核流程」
第三輪（若仍不足）：英文同義詞 → 「performance review」OR「annual review」
```

## 混合搜尋：不是二選一

成熟的企業搜尋系統通常不會只選一種搜尋方式，而是結合兩者的優勢，稱為 **Hybrid Search（混合搜尋）**。

<Steps>
  <Step title="並行執行兩種搜尋">
    同時執行關鍵字搜尋（BM25）與語意向量搜尋，分別取得各自的候選結果集。
  </Step>
  <Step title="分數融合（Score Fusion）">
    將兩種搜尋的分數透過加權平均或 RRF（Reciprocal Rank Fusion）等方式合併，產生統一的排名。
  </Step>
  <Step title="重排序（Reranking）">
    可選擇性地使用 Reranker 模型對合併後的結果做二次排序，進一步提升最終結果的相關性。
  </Step>
</Steps>

<Tip>
  在未來的進階架構中，還可以加入 **Metadata Filter**（依文件類型、時間範圍、部門過濾）與 **Query Expansion**（自動擴展查詢詞彙），讓搜尋結果更精準、更穩定。
</Tip>

## 踩坑筆記：相似度分數不是絕對的

<Warning>
  不同的 Embedding 模型與向量距離計算方式，分數的分布範圍可能完全不同。在 A 模型下，相似度 0.75 代表高度相關；在 B 模型下，0.75 可能只是普通相關。不要把在某個模型上調好的門檻，直接移植到另一個模型上。門檻設錯，可能把所有相關內容都過濾掉。
</Warning>

設計搜尋過濾條件時，建議：

1. 先用實際的查詢樣本觀察分數分布
2. 設定相對寬鬆的門檻，再依需求調整
3. 記錄並監控不同查詢類型的命中率，持續優化

<Accordion title="補充：Embedding 模型的選擇對搜尋品質的影響">
  不同的 Embedding 模型對不同語言、領域的理解能力差異很大。通用英文模型（如 OpenAI text-embedding-3-small）在中文語意搜尋上的表現，往往不如專門針對中文訓練的模型（如 bge-m3、multilingual-e5）。

  在企業文件大量使用中文的場景，選擇適合的多語言或中文 Embedding 模型，對搜尋品質的影響可能遠大於 Chunk 大小的調整。
</Accordion>

</Info>
