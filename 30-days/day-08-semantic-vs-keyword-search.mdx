使用者問：「**離職後帳號怎麼處理？**」

但公司文件真正的標題可能叫做：「**離職者權限撤銷流程**」。

兩句話描述的其實是同一件事：員工離開公司後，應如何移除系統與帳號存取權限。但如果搜尋系統太依賴使用者輸入的字面詞彙，就可能因為「帳號怎麼處理」與「權限撤銷」的措辭不同，而無法把最相關的文件排到前面。

這正是企業搜尋中很常見的問題：**使用者通常用自己的語言描述問題，但文件使用的是公司的正式術語。**

理解關鍵字搜尋與語意搜尋的差異，是設計 RAG 系統的重要基礎。

## 關鍵字搜尋：先看「你輸入了哪些字」

傳統關鍵字搜尋，也常被稱為詞彙搜尋（Lexical Search），典型方法包括 BM25。它主要根據查詢詞與文件中實際出現的詞彙，判斷哪些內容比較相關。

以下用一個簡化案例理解：

```text
使用者查詢：
「離職後帳號怎麼處理？」

文件 A：
「離職後帳號處理方式與系統停用規則」
→ 字詞重疊高，容易被找到

文件 B：
「離職者權限撤銷流程」
→ 概念高度相關，但「帳號處理」與「權限撤銷」的表達不同

文件 C：
「年度帳號密碼更新政策」
→ 出現「帳號」，但實際主題並不是離職流程
```

關鍵字搜尋很擅長處理**精確詞彙**，例如：

- 員工編號
- 產品 SKU
- 合約號碼
- 系統名稱
- 法條條號
- 文件中確定會出現的專有名詞

但它的限制也很明顯：如果使用者不知道公司文件中的正式用詞，搜尋品質就容易下降。

<Note>
  圖 1 為了幫助理解，把關鍵字搜尋簡化成「可能找不到」的情境。實際的 BM25 並不是要求整句完全一致；只要仍有足夠的詞彙重疊，例如「離職」，它仍可能找到相關文件。真正的問題通常是：**相關文件排名不夠前面、被其他含相同詞但意思不同的文件蓋過，或使用者使用的詞與文件幾乎沒有重疊。**
</Note>

## 語意搜尋：先理解「你其實想找什麼」

語意搜尋（Semantic Search）的核心通常是 **Embedding**。

系統會把使用者問題與文件片段轉換成向量，讓意思相近的內容在向量空間中更靠近。搜尋時，不只是比較有沒有相同字，而是比較兩段文字在「概念上有多接近」。

以剛才的案例來看：

```text
「離職後帳號怎麼處理？」
            ↓ 語意相近
「離職者權限撤銷流程」
            ↓ 語意相近
「員工離職時停用系統存取權限」

            ↓ 語意較遠
「年度密碼更新政策」
```

雖然「帳號怎麼處理」與「權限撤銷」不是相同字詞，但它們都在描述同一個企業流程，因此語意搜尋較有機會把相關文件找出來。

這對企業環境特別重要，因為常見情況包括：

- 員工使用口語提問，文件使用正式術語
- 同一件事在不同部門有不同稱呼
- 中文、英文縮寫與內部術語混用
- 使用者只知道問題，不知道文件名稱
- 文件標題與內容使用不同表達方式

## 同一個問題，兩種搜尋方式怎麼看？

| 面向 | 關鍵字搜尋 | 語意搜尋 |
| --- | --- | --- |
| 主要依據 | 查詢詞與文件詞彙的匹配程度 | 問題與文件的概念相似度 |
| 最擅長 | SKU、編號、人名、正式術語 | 自然語言問題、同義詞、不同措辭 |
| 使用者需要知道正式用詞嗎？ | 通常比較需要 | 相對不需要 |
| 面對「帳號處理」vs「權限撤銷」 | 可能排名較低 | 較容易判斷為相近概念 |
| 可解釋性 | 較容易理解為何命中 | 需要搭配相似度與來源檢查 |

    - 「出差住宿最多可以報多少？」

  </Card>

## 為什麼 RAG 特別需要語意搜尋？

RAG 的使用者通常不是在輸入文件名稱，而是在**直接問問題**。

例如：

> 「離職員工是不是當天就要停掉系統權限？」

真正相關的文件可能寫成：

> 「Employee Offboarding Access Revocation Policy」

或：

> 「人員異動帳號停用與權限回收標準作業流程」

如果 RAG 只依賴字面搜尋，使用者必須先知道企業的正式術語，才能問出「搜尋系統喜歡的問題」。這與自然語言問答的目的正好相反。

語意搜尋的價值，就是讓使用者可以用自己的方式描述需求，由系統負責把問題對應到企業文件中的正式表達。

## Data Machi：Document Tool 如何使用語意搜尋

Data Machi 的 PDF 知識庫會先把文件切成 Chunk，再建立 Embedding 與向量索引。當使用者提問時，系統將問題轉成查詢向量，從索引中找出語意最接近的文件片段。

以下是概念化後的流程：

```python
# 教學用簡化範例

def search_documents(query: str, top_k: int = 5):
    query_vector = embedding_model.embed_query(query)

    results = vector_store.similarity_search_with_score(
        query_vector,
        k=top_k,
    )

    return [
        {
            "text": doc.page_content,
            "source": doc.metadata.get("source"),
            "page": doc.metadata.get("page"),
            "score": score,
        }
        for doc, score in results
    ]
```

因此，使用者即使輸入：

```text
離職後帳號怎麼處理？
```

系統仍可能找到：

```text
文件：離職者權限撤銷流程
段落：員工離職生效後，應於指定時間內撤銷企業帳號與應用程式存取權限……
```

這就是語意搜尋對 RAG 最直接的價值。

<Note>
  上述程式碼是為了說明概念而簡化。正式專案還需要處理 Chunk Metadata、文件範圍限制、索引持久化、錯誤處理與來源引用等細節。
</Note>

## 但語意搜尋也可能「想太多」

語意搜尋不是搜尋問題的萬靈丹。

例如使用者查詢：

```text
EMP-01837
```

這是一個精確識別碼。此時我們根本不需要模型理解「EMP-01837 的語意」，只需要精確找到包含這個代碼的資料。

又或者：

```text
「ISO 27001 A.5.18」
```

這類條號、標準編號或產品型號，關鍵字搜尋往往比純語意向量搜尋可靠。

因此真正成熟的搜尋策略，不是把所有搜尋都改成 Embedding，而是知道**什麼問題應該精確找字，什麼問題應該理解意思。**

## Hybrid Search：兩種方法一起用

企業 RAG 常見的進一步作法，是使用 **Hybrid Search（混合搜尋）**，同時保留關鍵字與語意搜尋。

例如使用者查詢：

```text
Okta 離職帳號撤銷流程
```

其中：

- `Okta` 是非常重要的精確關鍵字
- 「離職帳號撤銷流程」則具有自然語言語意

這種問題非常適合混合搜尋。

<Steps>
  <Step title="執行關鍵字搜尋">
    使用 BM25 或其他 Lexical Search 找出包含 `Okta`、`離職`、`撤銷` 等詞彙的候選文件。
  </Step>
  <Step title="執行語意搜尋">
    使用 Embedding 找出與「員工離職後移除系統存取權」概念相近的文件片段。
  </Step>
  <Step title="融合排名">
    將兩邊結果透過加權分數、RRF（Reciprocal Rank Fusion）或其他方式合併。
  </Step>
  <Step title="需要時再做 Reranking">
    對候選結果進行二次排序，把最符合完整問題意圖的內容排到前面。
  </Step>
</Steps>

```text
使用者問題
「Okta 離職帳號撤銷流程」
        ↓
┌────────────────┬────────────────┐
│ Keyword Search │ Semantic Search│
│ 精確抓 Okta    │ 理解離職撤權   │
└────────┬───────┴───────┬────────┘
         └───────┬───────┘
                 ↓
           Rank Fusion
                 ↓
        最終相關文件排序
```

## 搜尋結果還可以再加上 Metadata Filter

除了關鍵字與語意之外，企業搜尋常常還知道更多條件。

例如：

```text
問題：
「台灣員工離職後 Okta 權限怎麼處理？」
```

可以先使用 Metadata Filter：

```text
region = TW
policy_type = IT Security
status = Active
```

再在這個範圍內執行語意搜尋。

這樣可以避免找到：

- 已失效的舊政策
- 其他國家的流程
- 不相關部門的權限規範

所以成熟 RAG 的檢索通常不只是：

```text
Question → Embedding → Vector Search
```

而可能逐漸變成：

```text
Question
   ↓
Query Understanding
   ↓
Metadata Filter
   ↓
Keyword + Semantic Search
   ↓
Fusion / Reranking
   ↓
Relevant Chunks
```

## 踩坑筆記：相似度高，不代表一定正確

<Warning>
  向量搜尋回傳的是「語意上比較接近」，不是「已經證明就是正確答案」。如果知識庫裡有「新人帳號建立流程」、「離職帳號撤銷流程」與「帳號密碼重設流程」，三者都與帳號管理高度相關，因此搜尋結果仍需要合理的 Top-K、Metadata、Reranking 與回答查核。
</Warning>

另外，不同 Embedding 模型的分數分布並不相同。因此不要直接假設：

```text
similarity > 0.8 = 一定相關
```

較好的做法是：

1. 準備一組真實企業查詢
2. 標記每個問題應該找到哪些文件
3. 觀察不同模型與門檻的 Recall / Precision
4. 再根據實際結果調整 Top-K 與 Threshold

## 今天要記住的核心差異

<Info>
  關鍵字搜尋問的是：「文件裡有沒有出現這些字？」

  語意搜尋問的是：「這份文件是不是在談使用者真正想找的事情？」

  在企業 RAG 中，兩者通常不是競爭關係。最好的設計往往是：**該精確時精確，該理解語意時理解語意。**
</Info>

回到圖 1 的案例：

```text
使用者說：離職後帳號怎麼處理？

企業文件寫：離職者權限撤銷流程
```

人類一眼就知道它們在談同一件事。好的企業搜尋系統，也應該逐步具備這種能力。
