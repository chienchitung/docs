大多數 RAG 教學都假設 PDF 有乾淨的文字層，可以直接被解析和向量化。然而在真實的企業環境裡，情況往往複雜得多：古老的合約是掃描進來的影像、操作手冊裡有大量流程圖、系統截圖嵌在技術規格書裡、表格的欄位關係只能靠版面位置來理解。這些內容對人類讀者很清楚，但對只能讀取文字的傳統 RAG 系統而言，卻可能是完全無法讀取的黑洞。

## 企業文件的三種典型「骯髒」情況

<CardGroup cols={3}>
  <Card title="掃描頁與影像 PDF" icon="file-image">
    文件整頁都是圖片，沒有可提取的文字層。常見於年代久遠的合約、蓋章掃描的核准文件、或從紙本轉數位的舊檔案。
  </Card>
  <Card title="流程圖與結構圖" icon="diagram-project">
    用箭頭、方塊、顏色表達的業務流程或系統架構圖。圖中的文字雖然可能被 OCR 抽出，但流程的「方向性」與「關係」無法從文字中還原。
  </Card>
  <Card title="複雜表格與截圖" icon="table">
    多欄位的比較表、系統操作截圖、儀表板畫面。表格中的數字拆離欄位標題後，意義完全改變；截圖中的 UI 元素只靠文字描述難以準確還原。
  </Card>
</CardGroup>

## OCR 只是第一步，不是終點

OCR（Optical Character Recognition，光學字元辨識）能把圖片中的文字轉成可搜尋的字元序列。這是處理掃描 PDF 的必要起點，但它本身有根本性的侷限：

**OCR 抽取的是文字，不是語義關係。**

以一個流程圖為例：

```text
原始流程圖（人類看到的）：
[申請送出] → [主管審核] → [通過] → [財務核銷]
                         ↓ 拒絕
                      [退回申請人]

OCR 可能抽出的文字序列：
「申請送出 主管審核 通過 財務核銷 拒絕 退回申請人」

問題：
- 箭頭的方向消失了
- 「通過」和「拒絕」的分支結構消失了
- 這串文字對模型幾乎沒有意義
```

流程圖中的箭頭、畫面區塊與欄位的上下位置關係，在 OCR 結果中通常是亂序或遺失的。如果直接把 OCR 的輸出向量化並存入知識庫，模型得到的資訊可能比沒有還糟——它以為自己讀懂了，但實際上理解的是亂序的碎片。

## Data Machi 的三層內容處理架構

Data Machi 針對不同的內容類型，採用不同的處理策略，而不是用一套做法硬套所有情況。

<Steps>
  <Step title="第一層：PDF 文字層（直接提取）">
    對於有完整文字層的 PDF，直接提取文字內容，解析頁碼與段落結構。這是最快速、成本最低的路徑，品質也最穩定。
  </Step>
  <Step title="第二層：OCR 補充（按需執行）">
    當某頁沒有文字層（或文字層品質不佳）時，對該頁執行 OCR，將辨識出的文字補入該頁的索引內容中。系統會標記哪些頁面的內容來自 OCR，以便後續評估品質。
  </Step>
  <Step title="第三層：多模態視覺摘要（智慧理解）">
    對於含有圖表、流程圖、截圖的頁面，使用多模態模型（能同時理解圖像與文字的 AI 模型）生成結構化的視覺摘要。這份摘要會記錄：頁面的整體用途、圖中可見的文字、各元素之間的關係，以及不應與其他內容混淆的邊界。
  </Step>
</Steps>

### 視覺摘要的結構示意

```json
{
  "page": 12,
  "content_type": "flowchart",
  "visual_summary": {
    "page_purpose": "說明費用申請的審核流程與分支條件",
    "visible_text": ["申請送出", "主管審核", "通過", "拒絕", "財務核銷", "退回申請人"],
    "relationships": [
      "申請送出 → 主管審核（固定步驟）",
      "主管審核 → 通過 → 財務核銷（審核通過路徑）",
      "主管審核 → 拒絕 → 退回申請人（審核拒絕路徑）"
    ],
    "do_not_confuse": "此流程為一般費用申請，不適用於超過 10 萬元的專案採購"
  }
}
```

這份結構化摘要，遠比原始的 OCR 文字序列對模型更有意義。

## Lazy OCR：把成本延後到真正需要的時候

如果對每一份上傳的文件，都立刻對所有頁面做 OCR 與視覺摘要，處理時間和資源成本會大幅增加——即使大部分頁面根本從未被查詢到。

Data Machi 採用 **Lazy OCR（延遲 OCR）** 的設計哲學：

```text
文件上傳時：
→ 優先處理有文字層的頁面（快速、低成本）
→ 識別出哪些頁面沒有文字層（標記為待處理）
→ 暫不對這些頁面執行 OCR

使用者查詢時：
→ 語意搜尋命中某個未做 OCR 的頁面附近區域
→ 系統自動補做該頁面的 OCR 與視覺摘要
→ 結果存入索引，下次查詢直接使用快取
```

<Tip>
  Lazy OCR 的核心思想是：把成本延後到真正需要時才支付。對於一份 200 頁的文件，可能只有 20 頁是掃描頁，而使用者真正查詢到的，可能只有其中 3 頁。不必為了那 3 頁，提前付出處理全部 20 頁的成本。
</Tip>

## 踩坑筆記：圖文關係不總是確定的

<Warning>
  圖片與附近文字出現在同一頁，並不代表它們一定在描述同一件事。

  常見的陷阱：
  - 一張「錯誤示範」的截圖，出現在說明「不應該這樣操作」的段落旁邊
  - 一個流程圖是舊版本的，但旁邊的文字已更新為新版本描述
  - 表格中的備註欄位指向另一份文件的規定，而非本頁的主題
</Warning>

多模態摘要應明確標示「關係是否確定」，避免模型把相鄰但不相關的圖文內容，拼接成一個錯誤的結論。設計視覺摘要的 Prompt 時，要明確要求模型區分「圖中可見的事實」與「圖文之間的推論關係」。

<Accordion title="補充：多模態模型在企業文件處理中的潛力">
  近年來，GPT-4o、Claude 3、Gemini 等多模態模型的圖像理解能力大幅提升，已能相當準確地解讀複雜的流程圖、組織架構圖與表格。

  在企業 RAG 系統中，多模態模型的典型應用包括：
  - 為掃描頁生成高品質的文字摘要
  - 解析複雜表格的欄位結構與數值關係
  - 理解系統截圖的操作步驟
  - 描述圖表所呈現的趨勢與比較關係

  但需要注意：多模態處理的成本（API 費用與處理時間）顯著高於純文字處理，應優先用於真正需要視覺理解的頁面。
</Accordion>

<Info>
  今天只要記住一件事：企業 RAG 不只是在搜尋文字，也要處理文件的版面與視覺語意——OCR 是起點，不是終點。
</Info>
